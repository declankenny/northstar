# Northstar: specification

Status: version 0.x, so anything may change between minor versions. Northstar tracks a household's net worth over time from balances entered by hand, and every feature described here is built.

This file records what the code cannot tell you: what Northstar is for, what it will and will not do, and the rules its data must obey. The reasons behind decisions are in `decisions.md`, and what is planned but not built is in `roadmap.md`. Screens, layouts and endpoints are not described anywhere in prose: the code and its tests are the reference. A change to a rule here ships in the same pull request as the code. Anything marked TODO is unresolved: do not guess it.

## Purpose

Track a household's financial position over time. Northstar records dated balances for each account and shows net worth and per-account history. Entry is manual.

## Scope

**Included**

- Accounts with a name, a class (Asset or Liability) and a configurable type.
- Dated balances per account, entered by hand, with one way to update many accounts at once.
- Importing dated balance history from a CSV file into one existing account, with the columns and the date format chosen by the person and a review before anything is written.
- Exporting one account's balances to a CSV file.
- Exporting what a list shows, as it is searched, filtered, sorted and grouped, to a CSV file (see "Exporting a list" under Rules).
- A list of every balance across all accounts, with its value in the account's currency and in the system currency, which a person searches, filters, sorts, groups and pages, and for which they choose the columns and their order (see "user_list_prefs" and "list_filters" under Data model).
- A list of every account, with its type, class and currency, its last balance (in the account's own currency and in the system currency), the date and age of that balance and whether it is stale, which a person searches, filters, sorts, groups and pages, and for which they choose the columns and their order. It opens with the shared filter "Open accounts", and an account's name opens its page, which has every action on the account (adding an account is a button above the list).
- A page for each balance, opened from that list, where its amount and note are changed or it is deleted, with the rules of the account page. Its date is not changed there: a balance is the one of an account on a date.
- A register of past imports, for admins, with an undo of an import that nothing has changed since.
- Net worth over time and per-account balance history, as charts and tables. An account's page lists its balances, newest first, twelve to a page, as a fixed list: the date, the balance and its change from the balance before it, in the account's own currency. A person can sort it and page it and nothing else: it has no search, filters, grouping, choice of columns or page size, or export, and nothing is saved for it. A balance's date opens its page, where it is changed or deleted, so the account page has no Edit or Delete for a balance.
- Closing an account to declutter, without losing its history.
- Local sign-in for a household: admins and ordinary users, a light or dark theme, and a first-run setup page that creates the first admin and the installation's first settings.
- System properties: named settings for the whole installation, which admins view and change.
- A Reports page, second in the navigation, that shows one report at a time at its own address: figures, charts and tables in the system currency that a person asks for with a few choices (such as a date) and an optional filter (see "Reports" under Rules).
- A currency for every account, from the ISO 4217 catalog, and one system currency for the installation. Each account is in the system currency or in another enabled currency, chosen when it is created and shown in that currency everywhere, and household totals are converted into the system currency with exchange rates an admin enters (see "Currencies" and "Exchange rates" under Rules).
- A number and date format for each person (their locale), from a short catalog, with a system default for new users. It decides how amounts and dates are shown and typed, and nothing else (see "Locale" under Rules).
- A list of the currency catalog for admins, with each currency's decimal places, whether it is enabled and how many accounts use it, which an admin searches, filters, sorts, groups and pages, and for which they choose the columns and their order, and a page for each currency where an admin switches it on or off, sets the date its rates start from and keeps its rates.

**Not included yet**

These are left out of the current release to keep it focused, not ruled out. Their GitHub milestones say when, and `roadmap.md` says why.

- An export of every account in one file, and of notes, sources or currencies.
- Fetching exchange rates from a provider (Frankfurter) once a day, in the in-app scheduler, with an admin still able to enter or correct any rate by hand. Crypto is not a currency here: a balance held in crypto is entered as its value in the system currency at the time. Existing balances stayed valid when currencies arrived because they were US dollars.
- Transactions, opening balances and reconciliation.
- Bank feeds, starting with SimpleFIN.
- Budgets and categories.
- Savings goals (backlog: might be done, not yet scheduled).
- Loan schedules. A loan is a liability with a balance history.

**Not planned**

- Investment positions or holdings, tax reporting and bill payment. Each would need a concrete use case and its own design.

## Data model

**account_classes**: id, name. Exactly two rows, Asset and Liability, loaded when the database is created and not editable.

**account_types**: id, name, class_id, stale_after_days (whole days, at least 1), created_at. Admins add, rename and delete types. Starting list: assets are checking, savings, brokerage, retirement, other investment, real estate and other asset. Liabilities are credit card, loan, mortgage and other liability.

**accounts**: id, name, type_id, currency_id, is_open (default true), notes (optional), created_at. An account's class is its type's class and is not stored on the account, so the two cannot disagree. The name is unique among all accounts that are not deleted, open or closed, ignoring ASCII case (SQLite `NOCASE`, as for account types and users) and surrounding spaces, enforced by a unique index. `currency_id` is the account's currency (see "Currencies"). `deleted` marks a deleted account (see "Deleting").

**currencies**: id, code, name, minor_units, is_enabled, rates_start and the audit columns. The ISO 4217 catalog, loaded by a migration (see "Currencies"). `rates_start` is the date rates are wanted from, empty until the currency is first enabled and always empty for the system currency.

**exchange_rates**: id, currency_id, rate_date, rate (the exact decimal as text), source ("manual" or "provider") and the audit columns, unique on (currency_id, rate_date). One rate means 1 unit of the currency = `rate` units of the system currency on that date (see "Exchange rates").

**balances**: id, account_id, as_of_date, amount_cents (integer, in the minor unit of the account's currency), note (optional), source ("manual" now, which leaves room for a feed), created_at, updated_at. One balance per account per date.

**list_filters**: id, owner_id (empty for a shared filter), list_key, name, conditions (a JSON array the list engine checks, never SQL), is_default and the audit columns. A saved filter for one list. A person's own are private to them, and a shared one is seen by everyone who can see the list and is made, changed and removed by admins only. A person has at most one default filter for a list, and a list at most one shared default, enforced by the database; a list opens with the person's own default, else the shared one, else no filter. A name is unique for one owner (or among the shared) and list, ignoring ASCII case. A condition that names a column the list no longer offers is skipped when the filter is applied. The Accounts list comes with one shared default filter, Open accounts (Open is Yes), made by a migration, which an admin may rename, change or remove like any other.

**user_list_prefs**: id, user_id, list_key, page_size (10, 25, 50 or 100, or empty), columns (a JSON array of field keys, or empty) and the audit columns. A person's choices for a list, one row for each person and list, each of which a list falls back from to its own default when empty. Today that is how many rows a page shows and which columns it shows, in which order. The list must show at least one column, each at most once, and a saved column that the list no longer offers is dropped and said, never an error.

**users** and **sys_sessions** hold sign-in (see "Security"). **user_identities**: id, user_id, issuer, subject and the audit columns. It binds a person who signs in through the identity provider to a user, by the provider's exact issuer and subject, unique on (issuer, subject) and on (user_id, issuer). A binding is never deleted or changed (triggers refuse it), and it stays when its user is deleted, so a later sign-in cannot get around the deletion. Its logged fields are the user, the issuer and the subject. A user has an email, display name, password hash, admin flag, theme and locale. A new user's theme and locale, whether added from the page, the command line or by reactivating a deleted user, are the `ui.theme.default` system property (dark until an admin changes it) and the `ui.locale.default` system property (`en-US` until an admin changes it), and a user can then change their own.

**ref_locales**: tag, label, decimal_mark, group_mark, date_template, currency_position, currency_code_spacing, cldr_version. The number and date formats a person can choose, loaded by a migration from the Unicode CLDR and never written at run time (see "Locale" under Rules). A user's `locale` is one of its tags.

**system_properties**: id, name, data_type_id, value, allow_null, hint, read_only and the audit columns. A named setting for the whole installation, stored as text and checked against its data type (String, Integer, Lookup, Date, Time or Boolean) when it is set. See "System properties" under Rules. **ref_property_data_types** (id, name), **ref_property_lookups** (the allowed values of a Lookup property: property_id, value, label) and **ref_property_validators** (the feature validations that run for a property, by function name and order) are loaded by migrations.

**Audit columns and the system user**: every table except the `sys_` and `ref_` ones has `created_at`, `created_by`, `updated_at` and `updated_by`, and the two author columns are foreign keys to users. The writer fills them: a row is authored by the signed-in user who made it, an update stamps who changed it and when, and an update that changes nothing stamps nothing. The command line, the seeded rows and every row that existed before these columns were added are authored by the system user. It is the one `users` row with `is_system` set, with a reserved `.invalid` email and a password hash no password matches, and nobody can sign in as it: sign-in treats it exactly like an unknown email. It is hidden from the user list and cannot be edited, deleted or have its password reset. No real user may have an address ending in `.invalid`.

**Stable ids and the `sys_` prefix**: every table the application owns, apart from the `sys_` ones, uses `AUTOINCREMENT`, so the id of a deleted row is never given to another. A table the application writes for itself (`sys_sessions`, `sys_login_attempts`, `sys_login_transactions`, `sys_schema_migrations`) is prefixed `sys_`, has no audit columns, and is written without an operation. A table loaded by a migration and never written at run time (the lists a setting is checked against) is prefixed `ref_`, has no audit columns, is not logged, and is refused by the writer. `account_classes` is the same kind of table but predates the prefix, so it keeps its audit columns.

## Rules

- **Money**: amounts are integers in the minor unit of the account's currency, never floating point: cents for US dollars, whole yen for yen, thousandths for Kuwaiti dinars. The column is still called `amount_cents`. They are typed in the person's locale and the currency's own digits, such as 1,234.56 or -25.00 for dollars in US English, 1.234,56 in German and 1,234 for yen. More decimal places than the currency has is refused, never rounded, and so is an amount over 9,999,999,999,999 minor units (about $100 billion), whatever the currency.
- **Locale**: a locale is how numbers and dates are shown and typed. The supported ones are the rows of `ref_locales`: a decimal mark, a group mark, a date template, and whether a currency code goes before or after the number and what separates them. They are generated from CLDR by a developer tool into a reviewed migration, and nothing at run time reads CLDR. Three rules are not data: digits are grouped in threes from four digits, the minus is an ASCII `-`, and month names are English (the interface is not translated). The first six are `en-US`, `en-GB`, `de-DE`, `fr-FR`, `de-CH` and `ja-JP`. A person's locale is `users.locale`, a foreign key to the catalog, and an existing user is `en-US`. The system property `ui.locale.default` (a tag in the catalog, not locked) is copied to a user when they are added or reactivated, and changing it affects only users added afterwards. A person chooses their own on their profile, in the same panel as the theme, and it is saved as soon as it is chosen. An admin can choose one when adding a user, and the choice starts at the default.
  - *Typed amounts* are read in the signed-in person's locale (the command line reads US English) and the account's currency, using that locale's decimal mark and no other. Group marks are optional and must be well formed: groups of three, none after the decimal mark. A space, no-break space or narrow no-break space is one group mark where the locale's is a space, and `'`, `’` and `ʼ` are one where it is an apostrophe, and nothing else is changed, so arbitrary spaces are refused. More decimals than the currency has is refused, never rounded. The reading is the locale's: `1.234` is 1234 in German, because that is what a dot means there. A leading `$` is read only for US dollars.
  - *Saving under a format that has changed*: a page that takes typed money says which format it is using. The server compares it with the person's saved format in the same transaction as the write, and if they differ it refuses with a conflict (HTTP 409) that names the new format, writing nothing. It is checked first, so a draft that is also malformed is told about the format, not the amount. The page keeps what was typed, loads the new format and says what changed ("Your number and date format changed to German (Germany). Nothing was saved."), and reads the draft in the new format. A caller that names no format, such as the command line, is not checked. Nothing is checked when no amount was typed.
  - *Messages*: every message the application writes for a person, on the page and on the server (a refusal, a conflict, a count, a date inside a sentence), says its dates and numbers in that person's locale: dates by the locale's template and whole numbers grouped from four digits by its group mark. The server does it for the signed-in person's locale, so a refusal reads "There is already a balance on 01.09.2026" in German and "on Sep 1, 2026" in US English. Text written where nobody is signed in (the command line, an operator message) is in US English. Data that is not prose, such as a date in an API field, stays `YYYY-MM-DD` for the page to format.
  - *Reading as you type*: under an amount box, a line says how what is typed reads in the person's format and the amount's currency ("Reads as 1.234,56 EUR"), or why it cannot be read, in the server's own words. It is on adding and editing a balance, on adding an account with a balance, and on every row of the Update balances screen, and it is empty until something is typed.
  - *Shown* amounts are grouped from four digits, with the locale's marks, in the currency's own digits, and a negative amount has its minus first. A date fills the locale's template from the `YYYY-MM-DD` text without making a JavaScript `Date`. Counts use the locale's group mark. The text an amount box starts with has the locale's decimal mark and no grouping or currency, so it reads back exactly. The CSV export stays locale-independent.
- **Currencies**: the catalog is the ISO 4217 currencies that are not funds, metals, units of account or special codes, and have 0, 2 or 3 minor units, with ISO's own names. It is loaded by a migration from the published file and never edited by the application, and a currency is never removed and never changes its code or precision. An installation has one system currency, the system property `system.currency`: a code in the catalog, chosen once before the first account exists, locked by the same change that sets it, and refused if any account exists, deleted ones included. An upgraded installation that has any account is set to US dollars and locked, because every existing amount is a dollar amount; one with none is unset. While it is unset no account can be created, and the server refuses it. An account's currency is set when it is created and never changes: a trigger refuses it. The system currency is always enabled: saving it enables it, and a migration enables it on an existing installation. A new account is in the system currency, or in a currency that is enabled (`currencies.is_enabled`) and has at least one stored rate. An admin switches a currency on or off on its page, which saves at once: switching on needs the date its rates start from (kept when it is switched off, filled in from `currency.rate.start.default` the first time), and the system currency cannot be switched off or given a start date. The start date is an intent: it does not stop anything, and the page says which dates before the first stored rate have none. The Add account dialog and its API choose the currency: the dialog has a Currency box only when a currency other than the system currency can be used (enabled, with at least one stored rate), the system currency first, and the API takes an optional currency code, the system currency when it is left out. The opening balance is read in the chosen currency. Every amount of an account, on the Accounts list, its page, its balance dialogs, the Update balances screen and in a conflict message, is written, typed and read in that account's own currency, and the Accounts list and the Update balances screen have a Currency column; an account's page has a Currency tile. Only totals are in the system currency. Import reads amounts using the account's currency precision, and an export writes an account's amounts with its currency's digits. Amounts are shown as `$1,234.56` for US dollars in US English and with the currency code otherwise, placed and spaced by the locale (`JPY 1,234`, `1.234,56 EUR`). Admins see the catalog on the Currencies page, a list of the framework (see "user_list_prefs" and "list_filters" under Data model), which shows each currency as stored (the `is_enabled` flag as it is, and the number of accounts that use it, open or closed but not deleted) and does not know which currency is the system currency; it changes nothing, and each currency's code opens its page. It opens with no filter, and "enabled" and "in use" are filters a person makes.
- **Dates**: a balance date is a calendar date with no timezone, and cannot be in the future (in a manual tracker that is almost always a typo). The app has no other timezone logic than one rule: "today" is the date in the installation's time zone, the `system.timezone` system property, read in one `today()` function so tests can fix it. The property is an IANA zone name such as `America/Chicago`, checked against the zone database, and empty means UTC. While it is empty at startup and the `TZ` variable names a zone, the application copies `TZ` into it once, as a write by the system user, and from then on ignores `TZ` (a differing `TZ` is logged as a warning). Changing the zone moves where "today" begins by at most a day and changes no stored date. The current moment, `now()`, is always a UTC instant, whatever the zone. Row timestamps are stored in UTC.
- **Sign convention**: balances are stored as entered, the way a statement shows them, and the account's class says what they mean. A 250,000.00 mortgage is 25000000 on a liability account. Net worth is the sum of asset balances minus the sum of liability balances. A balance may be negative on either side (an overdrawn checking account, an overpaid card) and net worth needs no special case.
- **Net worth is one calculation**: `net_worth_on(date)`. Every series, total and chart only chooses which dates to ask about, and the server computes every number, so no net worth rule lives in the frontend. A balance is a recorded fact (an amount in the account's own currency on a date, unaffected by exchange rates), and an account's position on a date is derived: its latest balance on or before the date at the latest rate on or before it, whatever date the balance has, so it moves when a rate moves. Net worth is the sum of positions, and a report obtains them from one place (`northstar/positions.py`), which reads the same view, `account_days`, so a report as at a date equals the Dashboard. A series never starts before the first balance, because before that net worth is zero only because nothing was entered, and drawing it would look like a climb from zero.
- **Exchange rates**: only an admin enters a rate, on the page of a currency that is enabled or has an account (never the system currency, which needs none), for a date that is not in the future, as a positive decimal of at most 12 significant digits typed in the person's number format. A date that already has a rate is refused and its rate is corrected instead. A correction changes only the value (its source becomes manual) and says which dates it changes, from the rate's date until the next stored rate. A rate is never deleted and its date and currency never change (triggers refuse it). Every change is in the change log. The scheduler's job `currency.rates.fetch` fetches rates from Frankfurter (`https://api.frankfurter.dev/v2`) at the time in the Time system property `currency.rate.fetch_time` (18:00 until an admin changes it, and empty switches it off), in the installation's time zone. It collects every currency except the system currency that has a rates start and is enabled or has an open account. A request asks for `base` the currency and `quotes` the system currency, so the answer is 1 unit of the currency in the system currency, and carries only currency codes and dates. The fetch is insert-only: it adds a date that has no stored rate and never changes one, whether it came from the provider or an admin, and it stores every day the provider returns up to and including today, weekends included, with source "provider" and as the system user (operation kind `scheduled`, or `cli` from the command line). A date after today is dropped. From the rates the provider has supplied it fills two gaps for each currency, newest first: the days after the newest of them, and, once, the days from the currency's rates start to the day before the oldest of them, starting no earlier than the provider's own first date for that currency. Only a provider rate marks an edge, so a rate an admin typed or corrected, however far from the rest, never makes the fetched history look complete. A currency the provider does not list is skipped. A range is asked for in spans of at most 366 days, each span is checked whole (the right currencies, real dates, each rate a plain decimal of at most 12 significant digits and 12 decimals, no date twice) and committed on its own, a date outside the span being dropped because where the provider's data is sparse it also answers with the last observation before the span, and a span that fails stops that currency so a stored range never has a hole inside it. A currency with unusable rates is named in the run's failure after the others have been fetched and kept. Rates are read as the provider's own decimal text and never as floats. A provider that does not answer, is busy (429) or fails (5xx) is retried by the scheduler, which repeats the whole job and finds its place again from the rates it has stored, and any other bad answer is not retried. Nothing the provider says is logged or kept: a run keeps only a message written by Northstar. `python -m northstar.rates fetch` runs the same job in the foreground as a manual run, and is refused while a fetch is already running. A currency's page shows the fetch time, its time zone, the provider and whether the last run succeeded, failed or was interrupted, and rates from the provider are labelled Frankfurter.
- **Conversion**: household net worth, assets and liabilities are in the system currency. Each account is converted on its own with the latest rate of its currency on or before the date (a later rate is never used), as `round_half_away_from_zero(amount x rate x 10^q / 10^p)` for the currency's decimal places `p` and the system currency's `q`, in exact decimal arithmetic, and the converted amounts are summed. A zero balance is converted like any other and needs a rate too. A date on which an account has no rate to convert with has no net worth: the server refuses it and names the currencies, and never totals the others. A series instead starts at the first date from which every later date can be converted, says where it starts and which currencies have no rate before then, and is empty with that explanation when no date can. A single account's balances, history and chart are in its own currency and need no rate. Converted figures are never stored: the view `account_days` looks up each account's balance and rate for every day, and the conversion is done in Python.
- **Carry-forward**: net worth on date D uses each account's latest balance on or before D. An account with no balance by D counts for nothing. An account that is not updated keeps its old balance (staleness is the safeguard), and a new account makes net worth step on the day it first appears unless an earlier-dated balance is entered.
- **Class and type**: every type belongs to a class, chosen when the type is created. An account's class can be edited at any time, and the edit must pick a type in the new class. It changes net worth for every past date the account covers, so the person is told how many balances and from when. There is no audit trail. A type's class cannot change while any account uses it, deleted accounts included, and the database refuses it even if the app is bypassed.
- **Account names**: a name is unique across open and closed accounts, because a closed account keeps its name and history. A deleted account frees its name. Only ASCII case is folded, so names that differ only in non-ASCII case count as different. Adding or renaming to a taken name is refused, and the message says when the holder is a closed account. A database from before 0.2 may hold duplicates: the migration keeps the lowest id's name and renames each later one, in id order, to the smallest unused "Name (n)" with n of 2 or more.
- **Change log**: every change to a logged field of a household record is recorded, in the same transaction as the change. One user action that makes a logged change has one `sys_operations` row, with its kind (`ui_edit`, `bulk_update`, `import`, `undo`, `restore`, `cli`, `scheduled` or `oidc`), who made it (the system user for the command line) and when. Each record it changed has one `sys_record_changes` row: an `INSERT` with every logged field, an `UPDATE` with the fields that changed, before and after, or a `DELETE` with every logged field, as JSON that keeps integer cents as integers. One action changes a record at most once, and the app stops and rolls back if it tries to change it twice. `sys_audited_fields` says which fields are logged: not the id, `updated_at`, `updated_by`, `balances.version`, password hashes, themes or the system flag, but everything else, including who created a record and when. A change to nothing but unlogged fields (a theme, a password, the upgrade of a hash at sign-in) updates the row and who and when, and leaves no operation. A save that changes nothing writes nothing. A balance's `version` is the id of the operation that last changed it, and 0 for one that existed before the log. The log records committed changes to logged fields: it is not a complete security log, and no baseline of earlier data is written. The import register and undo read it, and so does a balance's history (see "Balance history").
- **Deleting**: deleting an account marks it deleted. It and its balances disappear from every screen and from net worth history, which changes to match, and the person is told how many balances go. Nothing is erased: the balances stay in the database, and restoring a deleted account is planned for v0.7, so until then there is no way to bring one back. A deleted account frees its name. Closing is the way to hide an account and keep its history visible. Every read of accounts and balances goes through the views `live_accounts` and `live_balances`, and a test fails on any other. A type can be deleted only while no account uses it, deleted accounts included because they keep their type, and the database refuses otherwise even if the app is bypassed, so deleting a type can never change financial history.
- **Closing**: an account can be closed only when its latest balance is zero or it has none, otherwise a final zero balance comes first (with a note, if the account left the household). Closed accounts leave balance entry and the everyday views, and stay visible in a closed list with their history. Net worth ignores whether an account is open, because carry-forward does the work: the final zero carries forward. Balances cannot be added, edited or deleted on a closed account until it is reopened. The close date is not stored, it is the date of the final zero.
- **Changing a balance**: a balance can be added, edited or deleted. Adding on a date that already has a balance replaces it. An edit that moves a balance onto a date the account already uses is refused. A note is optional, at most 500 characters.
- **Balance history**: a balance's page lists the changes the change log recorded for it, newest first, twelve to a page, as a fixed list that a person can sort and page and nothing else. A row is an INSERT or an UPDATE of a logged field of a live balance (the balance exists and its account is not deleted), so a deleted balance or the balance of a deleted account has no history, and a DELETE is never a row. Its columns are When (the operation's UTC date), By, Amount (the amount the balance had after the change, in the account's own currency), Current (Yes for the latest row only) and How (what made it: Manual edit, Update balances, CSV import with the file's base name, Import undo or Command line, and "note changed" when the change edited the note). A change to the note alone has the amount before it. A balance that existed before the log, or whose creation the log never saw, has one baseline row, "Entered", authored and dated as the balance was created, whose amount is the one before the first logged change (the amount now when nothing was logged), so earlier history is neither shown nor implied. A row also says whether its amount can be restored (see "Restoring a balance's value"). The list is the view `balance_history`, and its rows are keyed by the negative of the log entry's id (so two changes in the same second sort the later first) or, for a baseline row, by the balance's own id.
- **Restoring a balance's value**: a row of a balance's history whose amount can be restored has a Restore button, after which the person is asked to confirm. A row can be restored when it set the amount (a row that entered the balance, the baseline row, or a change that changed the amount, and not a change of the note alone) and its amount is not the balance's amount now, so the current row and a note-only row have none. The button is greyed out, with the reason, on a closed account and while the form on the page has changes that are not saved. The confirmation names the account and date, says "Replace $1,250.00 with $1,100.00 for this balance?" and that only the amount is restored, so the note stays as it is. Restoring changes the amount alone, by the person restoring it, as one operation of kind `restore` whose header names the history row and its date; it is a new change, nothing in the history is removed or rewritten, and the balance's date, note, source and every other balance are unchanged. It follows the rule of conflicting edits: it is refused, writing nothing, if the balance has been changed or deleted since the person opened it, and the refusal says who changed it and what it is now. A closed account, a row not in this balance's history and a row that cannot be restored are refused. After a restore the page stays open, shows the new value and says Restored for a moment, and the history has a new first row, "Restored · value of" and the date it put back. Anyone who may edit a balance may restore a value.
- **Conflicting edits**: a balance is edited, deleted or saved from the Update screen only if it is still what the person opened. The page remembers each balance's version (the id of the operation that last wrote it, or none for a date that had no balance), sends it back with the change, and the server refuses the change, writing nothing, if the balance has since been changed, deleted, or added. The check comes first, even if the new values would equal the current ones, and it is made in the same transaction as the write. Deleting is checked too, and so is a blank date on the Update screen (a balance added since is a refusal). A refusal says, for each balance, what it is now and who changed it and on what date, and the person decides: the edit dialog can show the current value, the Update screen keeps what was typed and marks the rows that moved on, so saving again replaces them knowingly. Rows the Update screen did not send are never checked. Adding a balance on a date that already has one still replaces it, as above.
- **Updating many balances**: one date for all accounts. A blank amount is skipped, and a zero must be typed. Saving a date that already has a balance edits it, and existing notes are left alone. Only the amounts the person changed are saved, so a row that was merely shown is never written back over someone else's change, and the form cannot be edited while a save or a date load is running. A save is all or nothing: if any amount is invalid nothing is saved and each bad row says why. Choosing another date writes nothing.
- **Importing balances**: a CSV file of dated balances is imported into one existing account, chosen before the file, and nothing else: it never creates or changes an account, and has no transactions or currency conversion. A closed account must be reopened first. It runs as four screens (choose the file, map its columns, review, result), nothing is written before Import is pressed on the review, and going back keeps the choices while choosing a different file starts again. Cancel, on each of the first three screens, and Exit, on the result, do what the browser's Back button does: they return to the page the import was opened from (the account when there is none), and Cancel asks first when a file is chosen and nothing is imported yet. The server keeps nothing between the screens and does not keep the file, so each request carries the file again and the uploaded content is never logged or stored.
  - *The file*: UTF-8, with or without a byte order mark; a header row and at least one data row; at most 2 MB and 20,000 data rows; standard CSV quoting; blank rows ignored. The delimiter (comma, semicolon or tab) is worked out from the file and shown.
  - *The columns*: Date and Balance are required and Note is optional, each one column, chosen by position, so duplicate and blank headers stay distinct. Any other column is ignored. Clear header matches are prefilled and every choice can be changed.
  - *Dates*: the format is worked out for the whole column, never row by row, from `YYYY-MM-DD`, `MM/DD/YYYY`, `DD/MM/YYYY`, `MM/DD/YY`, `DD/MM/YY`, `DD.MM.YYYY`, `DD.MM.YY` and month names ("Oct 31, 2026", "31 Oct 2026"). It is chosen for the person only when the data decides it, and when it could be read two ways (`01/02/2026`) the person chooses and cannot continue until they do. Dotted dates are always day first. A two-digit year is the most recent year not in the future that ends in those digits. The future-date rule applies as everywhere. A column that mixes formats is an error.
  - *Amounts*: read into integer minor units in the destination account's currency, using its precision (zero, two or three decimal places). The supported plain, thousands-separated and European number styles are detected over the whole column, independently of the person's locale. Equivalent styles are one choice; when styles give different amounts, the person must choose before continuing. The Balance mapping has an inline number-style picker and a preview of how the first value reads. Excess precision is refused, never rounded. A minus sign or parentheses means negative; a blank amount is an error, zero is valid, and liability signs are kept as written. Currency symbols are accepted without deciding the currency, and a Currency column is ignored, but when the file says another currency than the account's (a Currency column naming one, or amounts with a euro or pound sign in an account that is not in that currency) the review says so in a note that does not block the import, and nothing is converted. The review names the account's currency and displays amounts in its precision. Existing Northstar CSV files, recognised by their four standard headers and date/balance mapping, are always read as plain decimal amounts, independent of locale or detection; their format cannot be overridden. No currency conversion is performed.
  - *Existing dates*: a date that already has a balance is skipped by default, and replaced only when the person chooses, with the old and new amounts shown. An identical row is unchanged and not written. A blank note in the file keeps the existing note, so an import never clears one, and a note that differs counts as a difference. A date more than once in the file is an error on every record that has it, and none is chosen over another.
  - *Validation*: the whole file is read and every problem found in its rows is listed with its record number (the header is record 1, and a quoted multiline record counts once). A row is never dropped silently, and a file with any problem has nothing to import. Duplicate dates are reported once every row reads.
  - *The review and the commit*: the review lists the newest changes first, at most 200 of each kind, with complete counts, and the import still writes every one. The commit takes the account from the address only, repeats every check and is one transaction, all or nothing. It is refused, writing nothing and naming the dates that changed, if the file, the settings or any date in the file is not as it was when reviewed, whether the date was filled, edited, replaced or deleted, so submitting the same review twice cannot import twice. A refusal returns the person to a review that is up to date.
  - *Recording*: one import is one `import` operation, whose header holds the file's base name (never its folders), the policy, the date and number formats, the columns used by position and the counts, and never anything from inside the file. Every balance it writes has the source `csv`, and a replacement is logged with the old and new amount, note and source. An import with nothing to write writes nothing. An import can be undone (see "Imports register").
- **Exporting balances**: one account's balances are downloaded as a CSV file, from the account's page, for an open or a closed account and for any signed-in user, with no questions asked. The file has one row per balance, oldest date first, and four columns: `Account ID`, `Account Name`, `Balance Date` (`YYYY-MM-DD`) and `Balance Amount` (a plain decimal in the account's currency, such as `1234.56` or `-80.00` for dollars and `1234` for yen, with no symbol and no thousands separator, and the sign kept as stored). Notes, sources and currencies are not exported. Importing the file back into the same account maps its columns by itself and finds every balance unchanged.
- **Exporting a list**: a list's view is downloaded as a CSV file, for any signed-in user who may see the list. It has every row the list matches, in the list's order and with the person's own columns, however many pages that is, and an empty result is the header row alone. The columns are named as they read on screen (a related column with its path, "Account › Type"). The file is UTF-8 with a byte-order mark, so a spreadsheet shows accents correctly, with CRLF line endings, and a cell is quoted when it holds a quote, a comma or a line break. A date is `YYYY-MM-DD` (a timestamp as its UTC date), an amount a plain decimal in its own currency with no symbol or separator (the reporting value in the system currency), Yes and No are `true` and `false`, a missing value is an empty cell and a related record is written as its name. Text that starts with `=`, `+`, `-`, `@`, a tab or a carriage return gets an apostrophe in front so that a spreadsheet does not run it as a formula; a number, an amount or a date is never changed. It changes nothing the person has saved. It is distinct from the per-account export, which stays the format that an import reads back.
- **Imports register**: admins see a list of past imports, newest first and at most 25, with the import date (the UTC date), who imported, the account, the file name (the base name only), how many balances it added and how many it replaced, and, once an import can be undone, when it was reverted. It lists only imports that wrote something, shows no amounts or notes, and names the account as it is now, marking one that is closed or deleted. Only admins can see it, in the page and in the server.
  - *Undo*: each import that has not been undone has an Undo button, for any admin. It first says what it would do (delete the balances the import added, put back the amount, note and source of those it replaced) and writes nothing, and it runs only when the person confirms. It is all or nothing: it is refused, writing nothing, unless every balance the import wrote still exists and has not been written since (edited, deleted, or replaced by a later import) and its account is open (a closed or deleted account is refused with the reason). A refusal names up to 10 of the dates in the way, with a reason each, and how many more, and the person fixes those by hand and tries again. The checks run again when it is confirmed, so a change in between is a refusal and never an overwrite. An undo is one `undo` operation, in the change log like any other, and can be undone by nothing, and an import is undone at most once, so putting the balances back means importing the file again. Only imports can be undone: a single edit, an Update save or a change to an account is corrected by hand.
- **System properties**: a property has a lowercase dotted name (the first segment is its group), a data type, an optional text value, a hint, and flags for whether it may be unset and whether it is read-only. Properties are added and removed by migrations only, and a feature adds the properties it reads. Only a value changes through the application, and only on the System properties page and its API, which are for admins. Server code reads properties for every request. Every write of a value goes through one setting service, in one write transaction: it refuses an unknown or read-only property, normalizes the text (surrounding whitespace removed, and a blank submission means unset), refuses an unset value unless `allow_null`, checks the text against the data type (String at most 256 characters, Integer a whole number JavaScript represents exactly, Date a real `YYYY-MM-DD` date, Time `HH:MM` on a 24-hour clock, Boolean exactly `true` or `false`, Lookup one of at most 20 options), and then runs the validators named for the property, in order. A validator is a plain function that raises an error text for the person who made the change, or accepts, optionally locking the property in the same change. A Date is an ISO calendar date, edited with a date box and shown in the person's format. A Time is a time of day, `HH:MM` on a 24-hour clock with a leading zero, read in the installation's time zone and edited with a time box. A Boolean is stored as the text `true` or `false`, is read as a real boolean, can never be unset, and is edited as a Yes or No choice. The first to lock is `catalog_currency`, for `system.currency` (see "Currencies"), which also enables that currency when it is saved. `currency.rate.stale_days` (default 14) is how old the newest rate of a currency with an open account may be before its page warns, and `currency.rate.start.default` (default 2000-01-01) is the start date filled in when a currency is first enabled. `catalog_locale`, for `ui.locale.default`, accepts a tag in the locale catalog and does not lock. `iana_timezone`, for `system.timezone`, accepts a name in the zone database, does not lock, and takes effect for "today" as soon as the change is saved. The first refusal is shown as it is and nothing is written. A submission equal to the stored value writes nothing and runs no validator. There is no check for two admins saving the same property: the later valid save wins. Each change is in the change log. The settings of OIDC sign-in are in place before the sign-in itself, which is not built yet (see `docs/design/oidc`): `oidc.enabled`, `oidc.provider`, `oidc.issuer`, `oidc.client_id`, `oidc.user.allow_creation` (all off or unset), `oidc.session.lifetime_hours` (12, from 1 to 8,760) and `system.auth.local.enabled` (on). Their validators refuse a configuration that could leave nobody able to sign in: OIDC cannot be turned on until the issuer, the client ID, the client secret and the public address are all present (and, over HTTPS, `NORTHSTAR_COOKIE_SECURE=1`), cannot be turned off while password sign-in is off, and its issuer and client ID cannot be cleared while it is on; password sign-in cannot be turned off until OIDC is on and complete and an admin has signed in through it; and the issuer cannot change while password sign-in is off. The issuer is an `https://` address (plain `http://` only for localhost) with no query or fragment. The client secret is never a property: it comes from `NORTHSTAR_OIDC_CLIENT_SECRET_FILE` or `NORTHSTAR_OIDC_CLIENT_SECRET` (both set stops the app starting), and the public address from `NORTHSTAR_PUBLIC_URL`, an HTTPS origin that is never worked out from request headers (plain `http://` only for localhost, 127.0.0.1 and [::1]). `python -m northstar.signin enable-local` turns password sign-in back on from the host, as the system user, with no session and no provider.
- **Staleness**: an open account is stale when the days from its latest balance to today exceed its type's `stale_after_days`. An open account with no balances is also flagged. Closed accounts are never flagged. The Add type form starts a new type at the `system.balance.stale_days` system property, 35 days until an admin changes it, and the admin can type any whole number of at least 1. Starting values are 35 days for every starting type except real estate, which is 365. A type that changes rarely gets a large value, not a special "never stale" setting. The rule is written twice, in `northstar/staleness.py` and in the view `account_summaries` (for the lists), and a test checks that they agree.

## Technical shape

- **Stack**: Python, FastAPI and SQLite on the server. The interface is a React and TypeScript single-page app built with Vite and served by the same application on the same origin, so there is no CORS. The sign-in page is a page of that app like any other, and the server renders no pages.
- **Dependencies**: few, each with a stated reason, with versions pinned exactly. The pins include the base images (by digest) and the CI actions (by commit SHA). Dependabot proposes every update as a pull request, except a new major version of Node, which is moved to deliberately onto an LTS line. CI fails a pull request on a known vulnerability in the Python dependencies (`pip-audit`), in the frontend dependencies that ship in the bundle (`npm audit`), or in the built image (Trivy, HIGH and CRITICAL findings that have a fix). The same checks run weekly on `main`. The final image has no pip.
- **Architecture**: business logic lives in plain Python functions, separate from the routes. Routes call them and add no rules. Every write to the database goes through `northstar/writer.py`, as part of an `Operation` that carries the connection, the signed-in user (none for the command line) and the kind of action, and a test fails on any SQL write outside it. Sessions and failed-login tracking, which hold no household data, are written there without an operation. The JSON API under `/api` is internal and not a stable contract.
- **Transactions**: any operation that reads in order to decide and then writes (closing an account, changing a balance, the admin rules, a password change) runs inside one `db.write_transaction`, which takes SQLite's write lock at the start, so two requests at the same moment cannot both pass the same check. Operations that need several writes to succeed together use the same helper.
- **Schema**: changes ship as forward-only migrations, tested on a copy of a database first. A released migration is never edited. The schema is drawn in `docs/schema.md`, and a test fails when that diagram and a migrated database disagree, so a schema change updates the diagram in the same pull request. The runner can rebuild a table: a migration whose first line is `-- northstar: rebuild` runs with foreign keys off, and is rolled back unless the foreign key check, the integrity check and the survival of every index, view and trigger pass before it commits. Migrations are SQL files only. The record of applied migrations is `sys_schema_migrations`, which releases before 0.2 called `schema_migrations`; the runner moves it, and a database whose ledgers it cannot reconcile is refused without anything being deleted. Only the app migrates, when it starts. If a migration is pending, or the ledger still has its old name, it first writes a checked backup beside the database, to `backups/pre-migration-<version>-<UTC time>.db`, and does not start if that fails. The newest five of these are kept, and older ones are removed only after a migration has worked. A database that has migrations this version does not know, judged by the highest migration number, is refused with a message to run the newer version or restore a backup. The command line tools never change the schema: they refuse a database the app has not brought to this version.
- **Reports**: a report is a definition in code (its parameters, the sections of its result and a calculation) registered through a loader, and the framework in `northstar/reports` checks it when it is registered, checks every request and checks what the calculation returns, so a wrong answer is never shown. A calculation reads one read-only snapshot, never raw filters, and counts the accounts it is handed. A request names every parameter and the server fills in none; a date is never in the future where the report says so. Money is integer minor units, whole and at most 2^53 - 1. A hierarchy's values are signed and add up exactly, and area is a separate size a report chooses. A request that is wrong is a 422 with the path to the field, data that cannot answer yet (a missing exchange rate) is a 422 with a reason, and a broken report is a 500 with no result, each with a stable `code`. The Reports page shows one report at a time at `/reports/<key>` (`/reports` opens the first in the list). A report opens at its declared defaults every time, and nothing chosen is kept in the address, in the browser or in a person's preferences. Each choice is checked before anything is asked, nothing stale is shown under a choice that cannot be asked for, and an answer to an older question never replaces the answer to a newer one; a change to a valid choice recalculates at once, and a filter waits for Apply changes. A report's headline figures sit in the page header, and its other sections are laid out on a 12-column grid: each takes 1 to 12 columns (the whole width unless it says otherwise), in the order the report declares them, and the grid narrows with the page. A report can be filtered only if its definition says so. It is then filtered by everything the field registry offers from its population (the live accounts) except what it explicitly excludes: every date (by kind, so a date column added later is excluded too, on any path, including those of related records) and named fields (on whole path segments: excluding `type` excludes `type` and everything beneath it, excluding `type.name` only that field). A field or relation added to the registry is therefore available to every report that does not exclude it. A request that names no filters means the report's own opening conditions (which may be none), an empty list means none, and explicit conditions replace the opening ones. A condition on a field the report does not offer is a 422 that names the condition and the part (`filters`, its place, `field`, `operator` or `value`) and is never applied or dropped. A report whose exclusions or opening conditions the registry does not support is broken (a 500 with no result) whichever endpoint is asked first. Filtering only narrows the accounts the framework authorized, and what can be picked for a filter by a record (an account type) comes from those accounts.
- **Net Worth Bridge** is the second report: why net worth changed between an opening date and a closing date (closing today and opening a year earlier to begin with, closing strictly after opening, neither in the future), in the system currency. Each account's change is its value on the closing date minus its value on the opening date, each worked out as the Dashboard does (an asset adds and a liability subtracts, so a reduced debt is a positive change), a type's change is the sum of its accounts', and the opening balance plus the changes is exactly the closing balance. The header shows the opening balance, the change (with its share of the opening figure, and coloured green when it raised net worth and red when it lowered it) and the closing balance. Above the table is a waterfall: the opening balance, a bar for each type that changed, from the running total, with its signed change, and the closing balance, which are the same two figures as the header. It starts on a scale zoomed in below the lowest the running total reaches, not at zero. Clicking a type's bar, or its name under the chart, opens it into its accounts' bars in name order, with a bracket under them whose name closes it, and the table opens and closes the same types: opening or closing any mix of types changes no total and no net change. Expand all and Collapse all are above the chart, and an account's bar opens its page. The totals and every bar follow the filter, so filtered it is the bridge of the accounts chosen. The detail is a table of types, collapsed to begin with, that open to their accounts with opening, closing, change and the balances they rest on, and an account with no balance on the opening date says so. An account that did not change is never shown, and neither is a type with none left; a type whose accounts offset to zero stays. A change is the change in the balance and in exchange rates together. A missing exchange rate on either date stops the whole report. It can be filtered by any account field except dates and opens with no filters.
- **Assets & Liabilities** is the first report: what you own and what you owe on one date (today unless another is chosen, never in the future), in the system currency, from the same account positions as the Dashboard, so its assets, liabilities and net worth equal the Dashboard's for the same date and accounts. The page header has three figures, each with its number of accounts, and below it are two treemaps, assets and liabilities, each by account type and then account, sized by value; an account is the colour of its type, and a block too small to hold its label has none. Clicking a type, or its entry in the list under the chart, shows its accounts, and an account opens its page. A type's value and number of accounts include every account in it. An account that is overdrawn (an overpaid liability counts the same) or has no balance by the date cannot be drawn: it stays in the list, last in its type and marked "not in the chart", so the lists add up to the figures at the top. A balance in another currency with no exchange rate by the date stops the whole report and says which currency. It can be filtered by any account field except dates (it has a date of its own) and opens with no filters.
- **Packaging**: one container and one SQLite file on a mounted volume.
- **Scheduler**: the application runs its own jobs once a day, each at a start time held in a Time system property and read in the installation's time zone, from a registry in code (`northstar/jobs.py`, which holds the exchange-rate fetch). A job is due once per calendar date, at or after its start time, when it has no scheduled run for that date, so a daylight-saving day that skips or repeats the time runs it once, and a missed time is made up at the next tick, which includes the first after startup. There is at most one scheduled claim per job per date, and a crash after the claim means no scheduled attempt for that date, not a repeat. Each job has a lock in `sys_jobs`: a fresh token for each acquisition and a lease that the running job renews, and every commit a job makes checks the token and the unexpired lease in the same transaction, so a holder whose lease ran out cannot commit. Fetching and other outside work may overlap, which is harmless because it only reads. Expired locks are cleared, and their running rows marked abandoned, at the first reconciliation after expiry, the first step of every tick. Every run is a row in `sys_job_runs` with its date, who started it, its times, its outcome (running, succeeded, failed or abandoned) and a short message, and finished runs are deleted after 90 days. A job fails with one of a few categories and a message written in our own code, and neither a log nor a run keeps the text of an exception, because it can carry a URL with a credential. A retryable failure is retried three times with growing pauses within the job's deadline, then left until the next date, and a failing tick of the scheduler is logged and retried with a growing pause, never ending the thread. The scheduler runs one job at a time in its own daemon thread, started and stopped with the server, and stopping interrupts every wait. The lease, the pauses and the other numbers are constants in `northstar/scheduler.py`, not system properties. A manual run from a screen and a Jobs screen are not built.
- **Backup**: a live SQLite file is never copied by hand. `python -m northstar.backup create FILE` and `restore FILE [--replace]` use SQLite's online backup. A backup is checked and only then renamed into place, never overwrites a file, and leaves no partial file on failure. The check reads the migrations recorded in either ledger name and requires the tables that they create, so a file that records a migration but lacks its table is refused, while a backup made before a migration is still valid. A restore needs the app stopped and moves the old database aside instead of deleting it, under a name that never replaces an earlier preserved file. The tool prints counts only. A backup holds real data, password hashes and sessions, so it stays out of any repository and in a private place. Backups stay on the host, not in the in-app scheduler (see "Scheduler"): the operator guide gives a script for the host's cron that takes a backup nightly, keeps 30 days in the volume and copies them to another machine, and the off-machine copy is the operator's job.
- **Frontend rules**: dates stay as `YYYY-MM-DD` strings and the frontend never creates a JavaScript `Date`, so the no-timezone rule holds. Money stays integer cents. Routing is a small history router with no library, on clean paths from the site root. The server returns the app for any page address, and the names `api`, `login`, `setup`, `static` and `assets` are reserved for the server, so a new top-level server route must avoid the page names. An address that is not a page shows a "Page not found" screen inside the app, with status 200, because the list of pages lives only in the frontend.

## Security

- **Access**: every address, the app and every `/api` endpoint needs a signed-in user. Only the sign-in page (`/login`), its endpoint (`/api/auth/login`), the answer to which ways of signing in are on (`/api/auth/methods`), the two routes of sign-in through an identity provider (`/api/auth/oidc/login` and `/api/auth/oidc/callback`), the first-run setup page (`/setup`) and its endpoints (`/api/setup`), which refuse everything once an administrator exists (see "First admin"), the files of the app's build under `/assets/` and the files under `/static/` (the theme script and the icons) are public: the build holds the app's code and no data. Pages redirect to sign-in and keep the address asked for, and `/api` answers 401. Only a plain path on this site is kept: anything with a host, a scheme, a backslash, a space or a control character goes to the Dashboard instead.
- **Users and roles**: every signed-in user sees all household data, so there is no per-user data. Admins alone manage users, account types and system properties. There must always be at least one admin, you cannot delete yourself or remove your own admin, and a password reset or user deletion ends that person's sessions at once. An email is lower-cased and unique, and stays unique after a user is deleted.
- **OIDC identities**: after the provider's ID token has been validated, `northstar/identities.py` decides in one write transaction which user it is, and a refusal leaves no user, no binding and no session. A known identity (the exact issuer and subject) is its bound user whatever its email or name has become, and is never matched again by email, and a deleted or system user is refused. An unknown identity needs the claim `email_verified` to be exactly the boolean true, and a usable address. If that email is an active user's, the identity is bound to them and they sign in, even when creation is off, keeping their name and role. If it is a deleted or system user's, it is refused, and nobody is reactivated. If it is nobody's, a regular user is made only when `oidc.user.allow_creation` is on, with an unusable password, the system default theme and number and date format, and the provider's name if it is usable (not blank, printable, at most 100 characters) and their email if not. A user has at most one binding per issuer: a second subject presenting an already bound email is refused and never replaces the first. Every refusal for "no account", a deleted or system user, a conflicting binding and an unusable address gives one message, so the page does not say which. The new user and the binding are logged as the system user, in one operation of kind `oidc`.
- **OIDC sign-in**: the authorization code flow with PKCE (S256), asking for the scopes `openid profile email`. Only the ID token is used: nothing from UserInfo or a refresh token is kept, and the access token is never stored. `GET /api/auth/oidc/login?next=PATH` starts it and `GET /api/auth/oidc/callback` finishes it. The redirect address is `NORTHSTAR_PUBLIC_URL` plus the callback path, which must be an HTTPS origin (`http` only for `localhost`, `127.0.0.1` and `[::1]`). Starting makes a random state, nonce, PKCE verifier and browser binding. Only hashes of the state and the binding are stored, with the nonce, the verifier, the return path (a plain path on this site, checked again on return) and the settings fingerprint, in `sys_login_transactions`, for 10 minutes and at most 2000 at once. The binding is also sent as a cookie, `HttpOnly`, `SameSite=Lax`, `Secure` when the session cookie is, limited to `/api/auth/oidc`, and the callback refuses a return whose cookie does not match. A transaction is consumed by the first return that finds it, whether that return succeeds or not, so a login can be returned to once. A return made after the provider settings changed is refused. Every failure sends the browser back to `/login?oidc_error=CODE`, where the code is one of a fixed list (`not_allowed`, `email_unverified`, `not_configured`, `expired`, `provider_unavailable`, `cancelled`, `invalid_token`, `busy`, `throttled`): no text from the provider or from a token is ever shown, and the failure log carries a reason that holds no token, claim, address or secret. The ID token must be signed with an asymmetric algorithm that both Northstar accepts (RS, PS, ES or EdDSA) and the provider lists (RS256 when it lists none); `none` and the HMAC algorithms are refused. Its `iss` must be the configured issuer and its `aud` the client ID, with `azp` equal to the client ID when present and required when there are several audiences, and its `exp`, `iat`, `sub` and `nonce` are required and checked (60 seconds of clock difference allowed). The discovery document must name the same issuer and give HTTPS addresses. The signing keys are kept for an hour, and an unknown key makes the provider's key set be fetched again, at most once a minute. The client secret is sent by the method the provider lists (HTTP Basic first, then in the body). A browser that signs in through the provider has its previous session ended, so it holds one session. The session cookie is the same as for password sign-in, with the lifetime `oidc.session.lifetime_hours`. A session made by OIDC is ended at its next request when the issuer or client ID in the settings are no longer the ones it was made under. When `system.auth.local.enabled` is off, `POST /api/auth/login` answers 403 before anything is counted or checked.
- **The sign-in page and OIDC**: the page asks `GET /api/auth/methods`, which is public and answers only `local` (password sign-in is on), `oidc` (OIDC is on and fully set up, including the public address and client secret) and `provider` (the `oidc.provider` name, or null), with no issuer, client ID or secret, and is never cached. Until it answers the page shows only its heading, so a page with password sign-in off never offers a form, and if it cannot be asked the page shows the password form and no provider button, because the server refuses whatever is not allowed. With OIDC on, the page shows a "Continue with" button (the provider's name, or "your identity provider") above the password form with the line "or use your password", and with password sign-in off the button alone. The button goes to `/api/auth/oidc/login` by navigating there with the address asked for, not by submitting a form, because the page's content security policy allows forms to submit only to this site and the redirect on to the provider would be refused. Nothing in the page decides who may sign in. A failed provider sign-in comes back as `/login?oidc_error=CODE` and the page words it: "This account can't sign in to Northstar. Ask a Northstar admin for access." for `not_allowed`, "<Provider> hasn't confirmed your email address. Verify it there, then try again." for `email_unverified`, and "Couldn't reach <provider>. Try again, or use your password." for `provider_unavailable`, leaving out the password advice when password sign-in is off. Every other code, and any unknown code, has its own plain sentence, and the code itself is never shown. Users has a Sign-in column that says Local, OIDC or Local and OIDC (the word OIDC, never the provider's name), and None for a user with neither a password nor a binding. A user "signs in locally" when their password is usable and "through OIDC" when they have a binding to any issuer. An admin's reset-password dialog tells them when the user has no password today and that setting one also lets that user sign in with it while password sign-in is on. Someone with no password sees, in place of Change password on their Profile, that they sign in through the provider and have no password to change there.
- **Deleting a user**: a deleted user keeps their row, so the author columns that name them keep pointing at a real person. They cannot sign in (sign-in treats them exactly like an unknown email), are hidden from the list, and cannot be edited or have their password reset. Their password hash is replaced so it cannot be used. Adding their email again reactivates the same row: the id and creation metadata are kept, the display name, password and admin flag come from that request (an admin flag left out gives a regular user), the theme is the system's default theme as for any new user, and their old password and sessions stay dead. The system user cannot be reactivated. The admin rules count live admins only.
- **Passwords**: scrypt from the standard library at N=2^17, r=8, p=1 (128 MiB and about half a second per hash), at least 12 characters and no other composition rules. A hash carries its own cost, so the cost can be raised later: a hash made with a lower cost still verifies and is replaced by one at the current cost the next time its owner signs in, and a stronger one is never weakened. At most two hashes run at the same time, so a burst of sign-ins queues instead of using all the memory. A stored hash that asks for an unreasonable cost is refused without being computed. A wrong password and an unknown email give the same message and take about the same time (the hash for unknown emails is built at startup, so even the first miss costs the same). Changing or resetting a password ends the other sessions. A user who signs in only through the identity provider has an unusable hash, the same marker the system user and a deleted user have, so no password matches it. Password sign-in refuses such a user exactly like an unknown email, and takes as long: it spends a real hash on the dummy one, so the time does not show that the account exists. An admin can give them a password.
- **Sessions**: a random token in an `HttpOnly`, `SameSite=Lax` cookie, valid 30 days from sign-in and not extended on use. Only the token's SHA-256 is stored. The cookie is marked `Secure` when `NORTHSTAR_COOKIE_SECURE=1`, which must be set whenever the app is served over HTTPS, and the app logs a warning at startup when it is not (any value other than exactly `1` counts as not set). The app's own default is off, and the compose files default it to `1`. Any change made from a page of another site is refused. A session also records how it was started, `local` or `oidc`. An OIDC session lasts `oidc.session.lifetime_hours` from sign-in, is not extended by use, and carries a fingerprint of the issuer and client ID it was made under, which is set exactly when the method is `oidc`.
- **Throttling**: failed sign-ins, and wrong guesses of the current password on Change password, are limited: 5 in 15 minutes per email from one address, 30 in an hour per email from any address, and 20 in 15 minutes per address for any email (the last only when the address can be trusted). A blocked attempt answers 429 with `Retry-After`, never checks the password, and is not recorded. Unknown emails are counted like real ones, and only hashes of the email and address are stored. Behind a reverse proxy, `FORWARDED_ALLOW_IPS` must list the proxy for the real addresses to be used. If it does not, the app notices, turns the address limit off, and logs a warning. The two OIDC routes use the same limits, with starts and returns each counted under a name an email can never be: 5 in 15 minutes from one address and 30 in an hour from all addresses for each, and the 20 per address in 15 minutes is shared with password sign-in. A start counts until the sign-in it began succeeds, so five starts that are never finished within 15 minutes block that address for a while. A return that cannot be trusted (an unknown or reused state, a wrong browser binding, an invalid token) counts, and a success clears both counts. A provider that is down, a person who turned the request down and a person the household has not allowed do not count.
- **Headers**: every response carries a content security policy that allows only the app's own scripts, styles, images, fonts and connections, no inline script or style in HTML, no `eval`, no other site's content, and no framing of the pages, plus `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin` and a `Permissions-Policy` that turns off the camera, microphone, location, payment and USB. The pages must stay free of inline scripts, `style` attributes, style blocks and event handler attributes, and a test enforces it. The theme is applied by the file `static/theme.js`. HSTS is left to the reverse proxy.
- **First admin**: there is no default user or password. The first admin is made on the first-run setup page (`/setup`), which also sets the system currency, the default number and date format and the time zone, in one transaction. The administrator is created by the system user, because nobody is signed in. The properties are then saved as that administrator through the setting service (see "System properties"), so its validation and locking apply, a value that is unchanged writes nothing and keeps its author, and an existing locked currency is shown read-only and kept. The administrator gets the chosen number and date format, and it becomes the default for new users. The currency is required while it is unset, with none preselected, and is locked by being saved. A refusal of any field, or any failed write, saves nothing. Setup is available only while no administrator row exists, deleted ones included (the system user does not count), so deleting an administrator never reopens it. Once one exists, `/setup` goes to sign-in and the setup endpoints refuse. While setup is open, startup makes a random token and prints it once in the container log with the address: it is the one credential Northstar logs, on purpose, because the person who can read that log owns the machine. Entering the token in the page gives that browser a setup session, an `HttpOnly` cookie valid 30 minutes and not extended, which authorizes setup and nothing else. Giving the token, and a form that is refused, do not use it up, and an expired session is replaced by entering the token again. A restart makes a new token and ends every session. Only a committed setup ends them, in every browser, and a retry after a lost response is told that setup is complete and creates nothing. Wrong tokens are counted per address and refused after 5 in 15 minutes. An email that belongs to any user, deleted or not, is refused: setup never reactivates anyone. Nobody is signed in by setup, and the page leaves the email, never the password, for the sign-in page to fill in. The token and the setup sessions are held in memory, which relies on the app being one process, as the image runs it. There is no command that creates a user. `python -m northstar.users set-password EMAIL` resets a password and signs that user out everywhere. A way back in when no active admin remains is not built (see `roadmap.md`).
- **Outbound requests**: the exchange-rate fetch makes a request to Frankfurter over HTTPS that carries only currency codes and dates, with no credential, and a deployment that must not call out switches it off by clearing `currency.rate.fetch_time`. When OIDC is on, Northstar also calls the configured provider and no one else: its discovery document, its key set and its token endpoint, over HTTPS (plain HTTP only for localhost). Those requests follow no redirects, ignore the environment's proxy settings, verify certificates, give up after 10 seconds, and read at most 1 MB. The token request carries the client secret and the authorization code, and nothing of the household's data.
- **HTTPS**: the app serves plain HTTP and expects a reverse proxy to provide HTTPS. The operator guide, `docs/operating.md`, includes a Traefik example with the network, entrypoint and certificate resolver names as placeholders, and says that plain HTTP is for trying the app out only.

## Release and distribution

Northstar is open source (MIT, copyright Declan Kenny) for other people to run themselves, so it must be secure by default, have defined releases and be easy to install and update.

- **Versions**: semantic versions. Before 1.0 anything may change, with notes, and database migrations, environment variables and the backup format always count as breaking. From 1.0, the compatibility promise in `roadmap.md` defines what is breaking. Migrations, environment variable changes and backup format changes are always in the release notes.
- **Branches**: `main` is development. `release/X.Y` is cut when `vX.Y.0` is tagged, starting with `release/0.1`. A fix lands on `main` first and is backported, and each release is a tag `vX.Y.Z`. Only the latest minor version gets fixes until 1.0. Once the repo is public, rulesets protect `main`, `release/*` and `v*` tags: a pull request and passing checks are required, with no force-push or deletion.
- **Version**: written once, as `version` in `pyproject.toml`. The app reads it from the installed package and shows it, and the image carries it as a label. Tests fail if the frontend package declares another version or the changelog has no section for it, and the release workflow refuses a tag that does not match it or a changelog section that still has a TODO date.
- **Changelog**: `CHANGELOG.md`, in the Keep a Changelog format, has a section per version with a **Breaking** heading that says what an upgrade means for migrations, environment variables and the backup format, which always count as breaking before 1.0. A release's section is its release notes.
- **Community files**: `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`, issue templates for a bug and a feature request, and a pull request template with "What changed", "Verified" and "Not verified". Blank issues are off, and the issue chooser points security reports at private reporting.
- **Security policy**: `SECURITY.md` gives the supported versions, private reporting through GitHub, what to expect, the threat model and hardening notes for operators. Its threat model is the one in "Security" above: a household that trusts its own members.
- **Compose files**: `compose.yaml` is the user's file. It uses the published image with no `build:`, publishes the port on `127.0.0.1` only, keeps data in a named volume, drops all capabilities, and sets `NORTHSTAR_COOKIE_SECURE` to `1` by default. Its settings (`TZ`, `NORTHSTAR_PORT`, `NORTHSTAR_COOKIE_SECURE`) come from a `.env` beside it, and `.env.example` lists them with their defaults. `TZ` is only the first-start value of the `system.timezone` property. The developer build is `compose.dev.yaml`. The image runs as UID 1000 and has a health check that requests the sign-in page.
- **Publishing**: pushing a tag `vX.Y.Z` (or `vX.Y.Z-rc.N` for a release candidate) runs the release workflow. It refuses to publish unless the tag matches the version in `pyproject.toml` and `frontend/package.json` (a release candidate is `X.Y.ZrcN` in Python and `X.Y.Z-rc.N` in npm), `CHANGELOG.md` has a section for the version (a final release also needs a real date, not a TODO), the tagged commit is on `main` or a `release/*` branch, the tests and the image scan pass again, and that version has not been published before. It then pushes the image `ghcr.io/declankenny/northstar` for amd64 and arm64 with build provenance, tagged `X.Y.Z` (never reused) and, when no higher version holds them, `X.Y` and `latest`, and creates a GitHub Release whose notes are the changelog section. A release candidate gets only its own tag and is marked as a pre-release. The package must be public, which is a one-time setting on GitHub that the workflow cannot make. Updating is `docker compose pull && docker compose up -d`. A rollback is a restore of the pre-migration backup under the old image. The project keeps a `CHANGELOG`, a README quick start for trying it out and developing, and the operator guide `docs/operating.md` for installing, securing, upgrading and backing up a real installation.

## Acceptance for v0.1.0

- Accounts of every type can be created, and balances entered on arbitrary dates.
- Net worth on each date, and the month-end series built from it, match a hand calculation on a small synthetic dataset (automated test).
- Updating ten accounts takes one screen and one submit.
- Data survives a container restart, and a backup and restore has been tested.
- Tests use synthetic data only.
- Everything under "Release and distribution" is built, the image is published, and an install and an upgrade have been rehearsed from the published image on a clean machine.
