# Northstar: decisions

Why Northstar works the way it does. `spec.md` says what the rules are. This file says why, and what was rejected, so nobody has to rediscover it.

Entries are appended and never rewritten. To change a decision, add a new entry that says it replaces the old one. Dates start on 2026-10-31. Earlier decisions were made while v1 was built and have no recorded date.

Each entry: the decision, the reasons, and what would make us revisit it.

---

## Money and dates

### Money is integer cents, in US dollars only
Floating point cannot hold money exactly, and a rounding surprise in a financial total destroys trust in every number. Amounts are typed as dollars and cents and stored as integer cents. No currency is stored. A balance in another currency or in crypto is entered as its dollar value at the time. Revisit if multiple currencies are really needed: that means a currency per account, a rate per balance and rounding rules, with existing balances defaulting to USD.

### Dates are calendar dates with no timezone
A balance is "as of" a day, not an instant. Adding timezone handling would add bugs and no value for a household tracker. "Today" is the machine's date, read in one `today()` function so tests can fix it, and a deployment sets `TZ`. The frontend never creates a JavaScript `Date` (it counts whole days), because `new Date("2026-10-30")` is read as UTC midnight and shows as Oct 29 in the US. Revisit if one household needs two timezones, which is unlikely.

### Balances are stored as entered, with the class saying what they mean
A mortgage of 250,000.00 is stored as 25000000 on a liability account, the way the statement shows it. This matches how a statement and a balance sheet read, and it avoids sign mistakes when many balances are entered at once. Negative balances are allowed on either side, so net worth needs no special cases. Rejected: storing liabilities as negative numbers.

## Net worth

### One calculation, `net_worth_on`, with carry-forward
Net worth on a date uses each account's latest balance on or before it. Everything else (month-end series, charts, totals) only chooses which dates to ask about, so there is a single place to be wrong and a single place to test against a hand calculation. The accepted cost is that an account nobody updates keeps its old balance, so the stale flag is the safeguard, and a new account makes net worth step on the day it first appears.

### The frontend holds no net worth rules
The server computes every number the screens show, and the frontend only chooses dates and draws the answer. For the same reason the Update balances page shows each row's change as plain subtraction but no net worth preview: a preview would be a net worth rule in the frontend. Revisit by adding a server endpoint if a preview is ever wanted.

## Accounts and types

### Account types are configurable inside a fixed two-class model
Households have different accounts, so types are editable, but every type belongs to Asset or Liability, because the class is what net worth uses. Stale limits belong to the type, so all accounts of a type share a limit, and a type that rarely changes (real estate) gets a large number, not a special "never stale" setting. Admins alone manage types, while everyone can use them.

### Editing an account's class is allowed and rewrites history
People mis-classify accounts. The edit must pick a type in the new class and tells the person how many balances and from when it affects. There is no audit trail. Rejected: forbidding class changes, which forces delete and re-enter. Revisit if the lack of an audit trail causes real trouble.

### Deleting an account is allowed, deleting a type only when unused
Deleting an account removes its balances and says how many. Closing is the way to hide an account and keep history. A type can only be deleted when no account uses it, and the database enforces that with a restrict rule, so deleting a type can never change financial history.

### Closing only declutters, and needs a final zero balance
Net worth ignores whether an account is open. Closing requires the latest balance to be zero (or no balances), so carry-forward does the work and no special case is needed. The close date is not stored: it is the date of the final zero. Rejected: a closed-date column and special handling of closed accounts in net worth.

## Entering balances

### Update balances: all or nothing, no confirmation dialog, nothing written on a date change
A save with any invalid amount saves nothing and says which rows are wrong, so a batch is never half-applied. There is no confirmation dialog on Save: the change column, the "will replace" notes and the footer already show every change before it is made, saving is not destructive (saving the date again edits it), and a dialog on every save gets clicked through. A save sends only the rows the person changed, because resending the prefilled rows would write one person's stale values back over another person's changes. Two people changing the same row stays last-write-wins for now. The form is locked while a save or a date load runs, so an answer can never replace what was just typed. Changing the date writes nothing, and when amounts are typed it asks whether to keep them or clear the form. Leaving the page with typed amounts asks first, because losing ten statement figures is the costly failure. Revisit with a dialog for unusual cases only (overwrites, a balance that changes sign) if mistakes get through.

## Stack and architecture

### Business logic lives in plain functions, and the JSON API is internal
Routes call plain Python functions and add no rules, so a rule is written once and tested without a web server. The JSON API sits over the same functions. It is not a stable contract, so it can change with the frontend.

### A check and the write that depends on it run in one write transaction
Two requests at the same moment can both pass the same check if the check and the write are separate statements: a balance could be entered between "the latest balance is zero" and "close the account", leaving a closed account with a nonzero balance, and two admins could each demote the other and leave no admin. Every operation that reads in order to decide and then writes now runs inside `db.write_transaction`, which takes SQLite's write lock up front (`BEGIN IMMEDIATE`), so the second request waits and then checks against what the first left. Inside an open transaction it joins it. Rejected: database triggers for the invariants, because they hide rules inside the database away from the plain functions and their tests, and retrying on conflict, because a lock that makes the second request wait is simpler and household traffic is tiny. Revisit if writes ever become slow enough that waiting for the lock is noticeable.

### Everything is pinned, updates are reviewed pull requests, and known vulnerabilities fail the build
Python and npm versions, the two base images (by digest) and the CI actions (by commit SHA) are all pinned, so a build is reproducible and nothing changes without a diff. Dependabot opens the updates, and each one goes through CI and a review. The audits (`pip-audit`, and `npm audit` for the runtime dependencies that ship in the bundle) and a Trivy scan of the built image fail a pull request on a known vulnerability, restricted to HIGH and CRITICAL findings that have a fix, because a finding nobody can act on should not block anyone. Build-tool advisories in the frontend are reported but never fail the build, since a build tool cannot affect a running installation. The same workflow runs weekly on `main`, so a newly published advisory shows up there and not first on someone's unrelated pull request. Rejected: auto-merging updates (it would put unreviewed code in a release), and scans that only warn (a warning nobody is forced to read is not a control).

The final image has no pip. The first scan failed on five findings, all in libraries vendored inside pip itself (msgpack, urllib3 and an old setuptools) that the app never uses, so pip is uninstalled once the app is installed. That clears them for good, instead of ignoring them in a scanner configuration, and it means nothing can be installed into a running container. Revisit if something in the image ever needs pip at run time.

### One container and one SQLite file
Household scale, fewest moving parts, simple backup. A live SQLite file is never copied by hand: backups use SQLite's online backup, are checked before they are put in place, and restores move the old database aside.

### React, TypeScript and Vite, served by the same application
The most documentation, and it needs no second container. Same origin, so no CORS. Each frontend dependency needs a stated reason, and versions are pinned exactly.

### No chart library, and no router library
The net worth chart is one simple area drawn as SVG, so a chart library would be weight for no benefit. Routing is about 30 lines of our own code with a leave guard for unsaved work. `react-router` only offers a leave guard in its data-router mode. Revisit the chart decision when a second kind of chart is needed, and the router when routing outgrows seven pages.

## Security

### Local accounts, with no default user
The first admin is created from the command line with a password prompt, so there is nothing to ship or leak and no open signup route. Passwords use scrypt from the standard library, at least 12 characters and no other composition rules. A wrong password and an unknown email look identical in message and timing. Only a hash of the session token is stored, so signing out or changing a password really ends the session on the server. Every signed-in user sees all household data, so there is no per-user data and no per-user permissions beyond the admin role. OIDC is planned and not built.

### Sign-in throttling: three limits, so one attacker cannot block the owner, and a proxy is detected, not configured
Failed attempts are counted in sliding windows against three limits: 5 in 15 minutes per email from one address, 30 in an hour per email from any address, and 20 in 15 minutes per address for any email, the last only when the address can be trusted. A throttle, not a lockout, but any cap on an account can be used by a persistent attacker to slow its owner's sign-in, so the everyday limit is keyed on the email **and** the address: an attacker at another address trips only their own. The account-wide limit is deliberately high so that stopping an attack spread over many addresses does not make blocking the owner cheap. The limiter never looks at the users table and counts unknown emails like real ones, so the answers reveal nothing. A blocked attempt does not check the password, so a correct guess cannot get through, and is not recorded, so a block cannot extend itself. Only hashes are stored, because people paste passwords into the email box.

An attempt takes its slot before the password is checked, in one write transaction. Checking first and recording the failure afterwards would let many simultaneous requests all be checked before any failure was recorded: removing the transaction in a test let 14 of 30 simultaneous attempts through instead of 5.

Behind a proxy every request appears to come from the proxy, so counting by address would let one attacker block everyone, and trusting `X-Forwarded-For` blindly would let an attacker dodge the limit. Uvicorn already replaces the connecting address with the forwarded one only for proxies in `FORWARDED_ALLOW_IPS`, so the app reuses that, and has no setting of its own: if the header is present, the address is trusted exactly when it appears in the header's chain. Otherwise the address limit is off for that request and a warning tells the operator which variable to set. A spoofed header only switches the address limit off for the spoofer, and the email limits still apply. The same limits guard the current-password check on Change password, so a stolen session cannot be used to guess the password. Rejected: a limit of our own for trusted proxies (a second security-sensitive parser of a header, and real addresses would disappear from the access log), and a hard lockout (it hands strangers a way to lock out the owner). Revisit if a household shares one address that is not a real network address, as Docker Desktop can make it, and the address limit trips for everyone. (2026-10-31)

### A strict content security policy with no inline scripts or styles
Every response carries a policy that allows only the app's own files: `script-src 'self'`, `style-src 'self'` and nothing with `unsafe-inline` or `unsafe-eval`, plus `frame-ancestors 'none'`, `base-uri` and `form-action` limited to the site and `object-src 'none'`. For an app that holds a household's finances, a cross-site scripting hole is the worst case, and this policy stops injected script running even if one ever gets in.

The cost was small. The only inline code was the theme script, which sat in two places (the React page and the sign-in page); it is now one file, `static/theme.js`, loaded from the head so it still runs before the first paint. React's inline styles needed nothing: it sets them one property at a time through the browser's style API, which the policy allows, unlike a `style` attribute written into the HTML. That was checked in a browser across every page and dialog with a violation listener (which was first shown to catch a deliberately blocked script and style), not assumed. A test reads the HTML entry points and fails if an inline script, style attribute, style block or event handler attribute appears, so the policy cannot be quietly broken later.

Rejected: a per-request nonce or a hash for the inline script (it needs templating the React page or maintaining a hash, when a file is simpler and cacheable), `unsafe-inline` for styles (it would weaken the policy for a problem that does not exist), and setting HSTS in the app (it may be served over plain HTTP in a trial, where HSTS is wrong, and it belongs to the proxy that provides HTTPS). Not done, and possible later: `Cross-Origin-Opener-Policy` and `Cross-Origin-Resource-Policy`, and `Cache-Control: no-store` on pages and API responses that hold financial data. (2026-10-31)

### Password hashing: scrypt at OWASP's first-listed cost, with at most two hashes at once
The cost was N=2^15, r=8, p=1 (32 MiB, about 120 ms), below OWASP's minimum for scrypt. It is now N=2^17, r=8, p=1: 128 MiB and about half a second on a fast desktop (a Raspberry Pi will be several times slower, a couple of seconds at most, for something done rarely: sessions last 30 days). Of OWASP's equivalent settings this one costs about the same time as N=2^16 with p=2 (measured: 490 ms against 472 ms) but makes an attacker pay twice the memory, which is what scrypt is for.

Memory is the catch: a burst of simultaneous sign-ins could need 128 MiB each. So at most two hashes run at once and the rest queue. Measured with 12 simultaneous attempts on 12 different emails: all answered in 3.4 s and the server peaked at 319 MiB, where unbounded it would have been about 1.5 GB.

A hash already carried its own cost, so raising it needed no migration. What was missing is the upgrade: a hash made with a lower cost still verifies, and is replaced by a current one the next time its owner signs in with the right password (a stronger hash is never weakened). A stored hash that asks for an unreasonable cost (a corrupt or tampered row) is refused without being computed. The hash used for unknown emails is built at startup: building it on the first miss made that one miss take twice as long, which was found by timing a real server and would have told a patient visitor which emails exist. A known limitation: until each existing user has signed in once, their older, cheaper hash verifies faster than an unknown email, which a precise timer could notice. Nothing is deployed yet, so no installation has this window, and it would only recur briefly after a future cost increase. The test suite uses a minimal cost through a fixture, because it hashes hundreds of passwords (this cut its run from about 95 s to 40 s), and the tests about the cost set what they need. Revisit when real hardware shows sign-in is too slow. (2026-10-31)

### HTTPS comes from a reverse proxy
The app serves plain HTTP. Sign-in sends a password and a 30-day cookie, so over a network others can see, both could be read. The documentation shows Traefik (automatic certificates) and says plain HTTP is for trying the app out only. The `Secure` cookie flag stays opt-in through `NORTHSTAR_COOKIE_SECURE` because a trial over plain HTTP on a LAN address would otherwise fail to sign in with no explanation, and so the app logs a loud warning at startup when it is off. The value must be exactly `1`, so the warning also appears for a well-meant `true`, which would otherwise leave the flag silently off. (2026-10-31)

## Project

### Releases: semantic versions, a release branch per minor version, latest minor only
`main` is development and `release/X.Y` is cut at `vX.Y.0`. Fixes land on `main` first and are backported. This is more machinery than tags alone, but a project others run needs a place to ship a security fix without taking unreleased work with it. Only the latest minor version is supported until 1.0 so a solo maintainer is not committed to old lines. Rulesets enforce the protection once the repo is public. (2026-10-31)

### Docs: a short spec, one decision log, and no screen descriptions
The spec holds scope and rules, this file holds the reasons, the code and tests are the reference for screens and endpoints, and the roadmap becomes GitHub issues. Prose about screens, layouts and endpoints is a second copy of the code, and it had already drifted. Rejected: keeping the spec in Claude project files, because Claude Code cannot read them, changes would no longer be reviewed with the code, and contributors could not see them. (2026-10-31)

### The user compose file: the published image, loopback only, and a Secure cookie by default
`compose.yaml` is the file a user copies. It uses `image: ghcr.io/declankenny/northstar:latest` and never builds, and the developer build lives in `compose.dev.yaml`, which keeps the same service and volume so a local test container keeps its data. `latest` is the simplest example and moves only on a release; before 1.0 a new minor version can break things, so the upgrade documentation will say how to pin `0.1` for fixes only.

The port is published on `127.0.0.1` because a bare port is reachable from the whole network over plain HTTP, and Docker's own firewall rules bypass `ufw`. The container drops all capabilities and cannot gain privileges. The cookie flag defaults to `1` in the compose files, even when `.env` leaves it empty, because a missing Secure flag fails silently behind HTTPS while a Secure cookie on plain HTTP fails loudly. The app's own default is still off, so tests and a bare `uvicorn` run are unchanged. This narrows the HTTPS entry above: it is opt-in in the app and on by default in the compose files. A browser on `http://localhost` accepts the cookie (checked in the built-in Chromium browser; Safari is unchecked), but over a LAN address it is dropped and sign-in appears to do nothing, so a plain-HTTP trial on a LAN sets it to `0`. Rejected: `PUID`/`PGID` settings (they need a root start and extra capabilities, which conflicts with dropping them: the image runs as UID 1000 and a bind mount needs `chown 1000:1000`), and `FORWARDED_ALLOW_IPS` in the base file (only reverse-proxy users need it, and the proxy example in the operator documentation shows it).

The image has a health check that requests the sign-in page, which is public and does not touch the database, using Python's `urllib` so the image needs no curl. It shows whether the web server answers, not whether the database is healthy. (2026-10-31)


### One version, a changelog with a Breaking heading, and templates that point the way
The version is written once, in `pyproject.toml`, and everything else reads it: the app (from the installed package, so there is no second copy in Python), the image label (a build argument that CI reads from `pyproject.toml`, checked against the built image) and a test of the one other place a number is written, `frontend/package.json`. The release workflow will compare the tag to it, so a release cannot go out with an old version. A build from `main` between releases still says the last released version; a `.dev` suffix would fix that at the cost of a step in every release, so it waits until it matters. The app does not look for newer versions, because that needs a call to the internet from an app that holds financial data.

The changelog has a **Breaking** heading in every released version because migrations, environment variables and the backup format always count as breaking before 1.0, and someone who updates with a plain `docker compose pull` must be able to see whether that is safe. A test fails when the current version has no section. Blank issues are off so every report arrives with a version and a way to reproduce it, and the issue chooser sends security reports to the private form. The Code of Conduct is a shortened Contributor Covenant that names the same private form as its contact, because publishing a personal email in a public repository is the maintainer's choice to make. (2026-10-31)


### Updates: a backup before every migration, a refusal on a newer database, and only the app migrates
Updating with a plain `docker compose pull` must be safe by default, and a migration is the one step that cannot be undone by running the old image, because the old image does not understand the new schema. So when a migration is pending the app writes a checked backup first (the same online backup the backup tool uses), to `backups/pre-migration-<version>-<time>.db` beside the database, and does not start if that fails: a skip switch was rejected because it would be the first thing a person under pressure reaches for. A rollback is then the restore that already exists, under the old image. The newest five backups are kept. Migrations are rare and the files small, so keeping some history is cheap, and keeping them all would forget that they hold real data and password hashes. They are removed only after a migration has worked, so a restart loop on a broken migration cannot replace good backups with copies of the same state, and only files named like ours are touched, so a person's own backups in that folder are safe. They live on the same volume as the database, so they protect against a bad upgrade and not against losing the volume: an off-site copy is still the operator's job.

A database from a newer version is refused, because starting on it could read or write a schema the code does not understand. The test compares the highest migration number and not the set of names, and the two names that databases from before the squash recorded (`0002_users`, `0003_user_theme`) are listed so their higher numbers are not mistaken for a newer version. `python -m northstar.users` used to apply migrations so it worked on a fresh checkout, which was a convenience and a way to migrate with no backup. It now refuses any database the app has not brought to the current version, so the schema has one owner. The cost is that a host install without Docker starts the app once before creating the first admin. The first-run setup page planned for v0.2 removes that step for most people. (2026-10-31)


### Releases are made by a tag, with every check in a tested script
A tag is the only thing a person does to release: pushing `vX.Y.Z` runs a workflow that checks, tests, publishes the image and creates the GitHub Release. The checks live in `scripts/check_release.py` and not in shell inside the workflow, because a release is the one place a mistake is public and permanent, and a script can be tested without pushing a tag. It refuses a tag that does not match the version in the files, so an image can never say one version while the code says another, a changelog section that is missing or still has a TODO date, a commit that is on no release branch, and a version that already exists, because a published version is never replaced. A release candidate is `0.1.0rc1` in Python and `0.1.0-rc.1` in npm and as a tag, which are the same version spelled for each ecosystem, so the app honestly says it is a candidate during the rehearsal.

The release runs the whole CI workflow again on the tagged commit (it is a reusable workflow) instead of copying its tests and scan, so there is one definition of what must pass. `latest` and the `X.Y` tag move only when the release is the highest version that could hold them, so a late patch to an older version cannot pull `latest` backwards. Numbers are compared as numbers, because 0.10.0 is higher than 0.9.0. Jobs get only the permission they need: `packages: write` for the image and `contents: write` for the release, and values from the tag reach scripts as environment variables, never pasted into shell text (a test enforces both). It adds four actions (QEMU for arm64, Buildx, the ghcr login and build-and-push), pinned by commit like the others, and uses the `gh` command for the release instead of a fifth. The frontend is built on the build machine whatever the target architecture, since its output is the same files everywhere, which keeps the arm64 build from running Node under emulation. Provenance is built into the image by Buildx, which needs no extra permission, and the architecture of the image is checked after the push. Tested: the arm64 image builds and starts healthy under emulation. Not tested until the first real tag: the workflow itself. (2026-10-31)


### Operator documentation: a separate guide, and backups on the host's schedule
The README is for someone trying Northstar out or working on it, and `docs/operating.md` is for someone running it for a household: install, HTTPS with Traefik, every setting, upgrading and rolling back, backup and restore, and users. They are separate because the two readers want different things and because the README is where a visitor decides whether to stay, so it stays short. The guide's commands were all run for real, in a container and on a host install, and that turned up two things now in the text: a backup tool never overwrites a file, so names carry the time (a nightly job and a manual backup on the same day would otherwise collide), and `docker compose cp` into a stopped container works, which is what makes a restore from an off-machine copy possible without a running app.

Scheduling is left to the host's cron instead of a scheduler inside the app. A scheduler would be a second process or a background thread in a container that is meant to be one small web app, with its own failure modes, and cron is already there on every machine that runs Docker. What the app does itself is the backup before a migration. The off-machine copy is the operator's job, because the app cannot know where an operator keeps a safe place, and the guide says plainly that a copy on the same disk does not survive the disk. This closes the open decision that was recorded as a TODO in the spec. Revisit if people ask for backups from inside the app. The Traefik example uses placeholders for the network, entrypoint and resolver names, because they are properties of an installation and are not guessed. (2026-10-31)


### Correction: X-Real-IP beside X-Forwarded-For does not make a trusted proxy untrusted
The throttling entry above says headers uvicorn does not interpret, `Forwarded` and `X-Real-IP`, mean an untrusted proxy. That was wrong when they arrive together with `X-Forwarded-For`. The first real deployment behind Traefik (issue 48) showed it: Traefik adds `X-Real-IP` to every request it forwards, nginx is commonly set to as well, and the check for it ran first, so a correctly configured proxy always looked untrusted, the per-address limit stayed off and the warning told the operator to set what they had already set. The tests had only ever used `X-Forwarded-For`, so they encoded the same assumption.

Uvicorn acts only on `X-Forwarded-For`, so when it is present it alone decides: the address is real exactly when it appears in that chain. `Forwarded` and `X-Real-IP` count as an untrusted proxy only when `X-Forwarded-For` is missing, because the proxy then speaks in a way uvicorn cannot read. Nothing about safety changes: a visitor who connects directly and sends a made-up chain is still not in it and is treated as an unknown address, which only switches the address limit off for them, and the email limits still apply. The new tests send Traefik's real header set, and one runs the app behind uvicorn's own proxy middleware so the test checks what the server does and not what the code assumes it does. (2026-10-31)


### Code scanning: two checks made strict, two alerts dismissed as false positives
Turning on CodeQL gave seven alerts. Each was read against the code and tried with hostile inputs, and none was exploitable, but two were worth hardening because they rested on luck. `next` after sign-in was safe only because the response library percent-encodes a tab or newline: a browser drops those from an address, so `/<tab>/evil.com` would mean `//evil.com`, and nothing in our own check said so. It now refuses control characters, spaces, backslashes and any address that parses with a host or scheme. The page route that serves the React app asked the file system whether a file existed before checking that it was inside the build, which cannot leak anything because the answer was never shown, but is still the wrong order. It now builds the path, checks it is inside the build, and only then looks at the file system, and a test records every file-system question and fails if one is about anything outside. Both are covered by tests with the hostile inputs, not only the ones that happened to work.

Two alerts were dismissed with their reasons written on them. The stack-trace alert is about returning `str(error)` for our own validation errors, which are messages written to be shown to the user and not stack traces. The substring alert is a test asserting that a document mentions a URL. A scanner finding that is not a bug still needs an answer in writing, so a later reader can tell which is which. (2026-10-31)


### The roadmap: a position paper in the repo, the plan in milestones and issues
`docs/roadmap.md` says where Northstar is going and why the releases come in their order. What each release contains lives only in GitHub: a milestone per release, an issue labelled `epic` for each release's theme with the scope, open decisions and completion criteria in its body, and issues labelled `feature` for the work, usually as sub-issues of an epic and written when their milestone is planned in detail. `enhancement` keeps the meaning GitHub and the feature-request template give it, a request from a user not yet triaged, so a filter can tell what someone asked for from what is planned. The backlog is `epic` and `feature` issues with no milestone. This refines the earlier entry that said the roadmap becomes GitHub issues, and closes the open decision about how the roadmap is kept, which was a TODO in the spec.

Rejected: per-release scope in the roadmap file (it would be a second copy of the issues and drift as soon as planning edited them), draft issues on a project board (GitHub does not allow labels or milestones on a draft, and drafts are invisible to anyone browsing the repository's issues), and Discussions (too much for one maintainer until there is a community to discuss with). The spec's "Not included" list was a fence around v0.1, not a statement that those features are ruled out, so it now separates what is not included yet from what is not planned. Revisit if a second maintainer joins and the plan needs a board. (2026-11-01)

### 1.0 is a compatibility promise, not a frozen schema
Before 1.0, migrations, environment variables and the backup format always count as breaking. Keeping that rule after 1.0 would make every release that adds a table a major version, and transactions, SimpleFIN and budgeting all add tables. So from 1.0 a release is breaking only if it breaks the promise in `docs/roadmap.md`: existing data survives a supported upgrade with its meaning unchanged, balance-only accounts keep working, Northstar CSV from 1.0 on stays importable by every later release, configuration changes have a documented migration path, and a backup can be recovered by restoring it with the release that took it and then upgrading. The promise has a direction on purpose: an older release is not required to read a newer export, and restoring an old backup directly into a newer release is not promised, because only the app migrates and the command line tools refuse a database the app has not brought to their version.

Two things are settled before 1.0 because they shape the promise: multi-currency, which changes what a stored amount means for every account, and the relationship between a balance observation and a statement checkpoint, which statements in 1.1 build on. Multi-currency is planned for v0.3, so the entry above that keeps every amount in US dollars stands until then. (2026-11-01)


### Dependabot does not propose new Node majors
Dependabot proposed Node 25 (#37), which is not an LTS line and whose security support had already ended, while Node 24 is LTS with support until April 2028. Its checks passed, so the green build gave no warning that the move went from a supported runtime to an unsupported one. Node only builds the frontend and is not in the final image, but the build should still run on a supported release. So Dependabot ignores major updates for the `node` image. A move to a new LTS line is a deliberate change with its own pull request, and digest and patch updates within the current major still arrive, so security fixes in Node 24 keep coming. This narrows the rule that Dependabot proposes every update.

Rejected: ignoring only odd-numbered majors. From Node 27 every major becomes LTS and there is one release a year, so an odd-number rule would wrongly hide Node 27. ### Backup validation follows the recorded migrations, and the icon is a public static file
A backup is valid when it has every table that the migrations it records create, and the list is derived by running those migrations on an empty in-memory database, not kept by hand. The first list was the tables of the initial schema, so a database that recorded migration 0002 but lacked `login_attempts` was accepted, restored, and failed at the first sign-in (issue 53). Requiring `login_attempts` in every backup would have refused genuine backups made before 0002, which must stay restorable for upgrades and rollbacks. A hand-kept map from migration to tables would have needed someone to remember it for each new migration. Deriving it costs a few milliseconds per check and cannot go stale. Migrations this version does not know are skipped, because the app already refuses those databases itself. Restore now chooses preserved-file names that do not exist (a `-2`, `-3` suffix after the timestamp), because the timestamp has one-second resolution and `os.replace` overwrites (issue 54).

The sign-in page had no icon because `/favicon.ico` fell outside the login exemption, and in fact the app had no icon file at all: signed in, the page catch-all answered with the app's HTML. The icons are now files in `northstar/web/static/`, which is already public, and both entry points link them there, so no new public path was added. Only the browser-tab and iOS home-screen files are shipped (ICO, SVG, 32 and 16 pixel PNG, apple-touch icon). The web manifest, Android and maskable icons are for installing the site as an app, which v1 does not support, so they are left out until a need appears. (2026-11-01)

### The migration runner rebuilds tables, SQL only, and moves its ledger
The v0.2 schema work (audit columns, `AUTOINCREMENT`, tighter constraints) needs tables rebuilt, and SQLite cannot do that safely with foreign keys on: dropping `accounts` would cascade into `balances`. `PRAGMA foreign_keys = OFF` does nothing inside a transaction, so the runner sets it before the transaction begins, for migrations that opt in with `-- northstar: rebuild` as their first line, and puts it back and verifies it afterwards. Before commit it runs `foreign_key_check` and `integrity_check` and requires every index, view and trigger that existed before to exist after, because dropping a table silently takes its indexes with it. Row counts alone were rejected as proof. Ordinary migrations behave as before. Upgrades and the backup check's scratch replay now share one executor, `db.migrate`, so the replay cannot disagree with a real upgrade.

Migrations stay SQL-only. Python steps were considered for data backfills such as the duplicate-account rename in migration A, but SQL can do that rename (rank the duplicates, and put the account id in the suffix when "Name (n)" is taken), and a second kind of migration is cost with no current need. Revisit if a real backfill cannot be written in SQL.

`schema_migrations` becomes `sys_schema_migrations`, because every table that is not user data now carries the `sys_` prefix. A database with the old ledger counts as behind, so the rename is preceded by the validated backup like any migration. The old app, started on a migrated database, creates an empty `schema_migrations` and fails; the new runner drops that stray empty ledger, and only that. Two empty ledgers, a malformed one or two populated ones are refused with nothing deleted, because guessing which history is true could lose data. A database from a newer version is refused before any cleanup. The rename and the cleanup run in their own transaction before the first pending migration, rather than inside it, so a database with no pending migration can still be fixed. (2026-11-01)

### Account names are unique, and the migration renames old duplicates in SQL
Unique among all accounts, open or closed, ignoring ASCII case (SQLite `NOCASE`, the comparison account types and users already use) and surrounding spaces (the application's `strip()`). Closed accounts count because they keep their name and history, so a name cannot be reused until the closed account is renamed, and the message says so. The index is full (`accounts_name_unique`); migration B3 later makes it partial when accounts become soft-deletable. The check in `accounts.py` runs inside the write transaction and gives the message, and the index is the guarantee if the check is bypassed.

A v0.1 database may hold duplicates, so the migration renames them in id order: the lowest id keeps its name, each later one becomes the smallest unused "Name (n)" with n of 2 or more, using the first account's spelling. This stays SQL-only, as decided for the runner: in each group the k-th later account takes the k-th unused number, which gives the same answer as the one-at-a-time rule because two groups can never produce the same new name (a name ends in its own " (n)"). A test compares the SQL with the one-at-a-time rule on random names. The migration also asserts that no stored name is empty or untrimmed and stops with a rollback if one is, instead of guessing. Names that differ only in non-ASCII case stay different, which matches account types and users. (2026-11-01)

### Every write goes through one module, as part of an operation
v0.2 records who changed what, which only works if no write can happen around the recording. `northstar/writer.py` holds every INSERT, UPDATE and DELETE the application makes (migrations excepted), and a test scans the source and fails on any other. SQLite cannot intercept writes globally, so the guarantee is that test. A write takes an `Operation`, made once per user action, which carries the connection and the actor, instead of the actor being kept as hidden state on the connection, where a write without one would simply have no author. The business functions that write take `op` in place of `conn` and read through `op.conn`; reads keep taking `conn`. The command line's actor is `None` until the system user exists (migration B1).

This step changes no behaviour and uses the actor for nothing. The writer's `update` already returns whether anything changed and skips a write that would change nothing, because the change log needs that answer, and the one SQL-expression value in use (`updated_at`) is a `NOW` marker that is applied with a real change and does not count as one. Table and column names are checked against the live schema, never taken from the caller's text. Sessions and failed-login tracking are `sys_` tables in the design and need no operation, so they have their own functions (`sys_insert`, `sys_delete`) that cannot touch household tables, and the household functions cannot touch them. They are named `sessions` and `login_attempts` until migration B1 renames them. A batch form for the import waits for the import (step 8). (2026-11-01)

### Audit columns, stable ids, the system user and the `sys_` prefix (migrations 0004 and 0005)
Every household table gets `created_at`, `created_by`, `updated_at` and `updated_by`, with real, required foreign keys to `users`, so history can always say who. Existing rows have no author, so the migration creates a system user and authors them with it, rather than allowing nulls (which would make every later query handle a missing author) or inventing a real person. The system user is an ordinary `users` row flagged `is_system` (one only, by a partial unique index), with an unusable password hash and a reserved `.invalid` address. It takes the next free id, but the code finds it by the flag, never by number. It is refused at sign-in through the same path as an unknown email, so a wrong guess and an attempt on it cost the same, and it is hidden from the user list and from every user action. The command line has no signed-in user, so its actor is the system user.

`AUTOINCREMENT` on every household table means a deleted id is never reused. `balances` and `account_types` are hard-deleted, and undo (later in v0.2) reinserts a deleted row under its original id, which is only safe if no other row could have taken it. SQLite cannot add it to an existing table, so 0004 rebuilds the five tables, in one migration run with foreign keys off by the runner, which then checks the keys, the integrity and that every index survived. The `sessions` and `login_attempts` renames are a second file, 0005, because renaming an index drops the old name and the runner's rebuild guard rightly insists no index disappears; a rename is not a rebuild.

The writer owns the audit columns: a caller cannot set them (it raises), `insert` stamps both authors, and `update` stamps the updater only when it really changes something. This replaces the `updated_at` expression that `balances.py` carried. Users are still hard-deleted until the soft-delete migration, so deleting a user who authored anything fails the foreign key for now; that is accepted because v0.2 is not released until soft delete has landed. (2026-11-01)

### Users are soft-deleted, and adding the email again reactivates them (migration 0006)
Once `created_by` and `updated_by` were real foreign keys (migration 0004), a hard delete of a user who had done anything would fail, and a delete that worked would leave history naming nobody. A `deleted` flag keeps the row, so history always points at a real person and no name needs copying into the audit columns. Deleting is one transaction: set the flag, replace the password hash with a value no password matches, and remove their sessions. A deleted user is treated everywhere as the system user already is: sign-in takes the same path, and the same dummy-hash work, as an unknown email, because verifying against the unusable hash would return at once and reveal that the account had existed.

Re-adding the email reactivates the same row instead of making a new one, as an explicit update through the writer, so one person is one row for good and the email stays globally unique (a partial unique index that freed the email for a second row was rejected: it would split one person's history in two). The request sets the display name, password and admin flag, so an admin flag left out gives a regular user even for someone who was an admin; the theme resets; the id and creation metadata are kept; `updated_by` records who reactivated them. The API says when an add was a restoration (`reactivated`), and the page tells the admin, so it is not mistaken for a new user. Migration 0006 is a plain column add and needs no rebuild. (2026-11-01)

### Accounts are soft-deleted, and every read goes through two views (migration 0007)
Deleting an account used to erase it and its balances for good, through the cascade. That is the one destructive thing the app could do to the money record, and the change log and undo in v0.2 need the data to still be there. So deleting now sets `accounts.deleted` and nothing else: the balances stay, and drop out of every view with the account, so net worth history changes exactly as it did before. Restoring is v0.6 (#58). The unique name index became partial (`WHERE deleted = 0`) so a deleted account frees its name; a closed account still holds it.

Reads go through `live_accounts` and `live_balances` instead of each query adding `deleted = 0`, so a new query cannot forget the filter, and a test fails on any direct read of `accounts` or `balances` outside the backup tool (which counts every row) and the account types module (which has to see deleted accounts). Balances are not soft-deleted themselves (a flag would touch every query on the money path); the view hides them through their account. The cost is that anything that rebuilds `accounts` or `balances` must drop and recreate the views, because SQLite cannot rename a table under a view; the migration, the schema notes and a test that shows the failure all say so. The writer now refuses to remove an account or user row at all, so the cascade can no longer erase history by accident.

A deleted account keeps its type, because restoring it must be possible and the database refuses to delete or reclass a type any account row uses. So a type used only by deleted accounts cannot be deleted until restore exists, and the app says so, counting live and deleted accounts together, instead of failing in the database. Letting a deleted account's type be cleared was rejected because it would break that promise. A restored account's name may by then be taken by a newer account; that is for the restore feature to handle. (2026-11-01)

### The change log: one header per action, one row per record, written by the writer (migration 0008)
v0.2 import and undo need to know what changed, to what, and by whom, and the audit columns only say who touched a row last. So every logged change is recorded as it is made: a `sys_operations` row for the user action and a `sys_record_changes` row for each record, with the logged fields as JSON (an update keeps only the fields that changed, before and after). One row per record rather than per field keeps an import of 20,000 rows to 20,000 rows, and one table serves every money table that comes later, where a table of changes per entity would not. Triggers were rejected: they cannot know the signed-in user or the action without hidden state on the connection, and they would need regenerating whenever a logged column is added. The writer already sees every write, and a test fails on any that bypasses it.

Which fields are logged is data (`sys_audited_fields`), with a row for every column, and a write whose table has a column without a row stops with an error, as does the schema test, so a new column forces the decision and a secret cannot be logged by accident. The registry is read once per operation and table, not once at startup as the design first said: a process-wide cache would have to be reset across the test databases and any restored database, and a read of a dozen rows once per user action costs nothing.

The header is written the first time a logged change needs it, so an action whose only changes are to unlogged fields (a theme, a password) leaves none, and an action that changes nothing writes nothing. A balance's version is the id of the operation that last changed it, which is why the header is allocated before the row. At most one change per record per operation is a unique constraint, and a second change is a programming error that rolls everything back, because two changes to one balance would share a version and undo could not tell them apart. An `Operation` is for one action and one transaction; reusing one after a rollback is refused, since its header no longer exists. The operation kinds are a lookup table, so a new kind (`integration`, when SimpleFIN arrives) is a one-row migration, not a rebuild. The table is the only list: the code keeps none, the writer checks a kind against the table when it writes the header (so a typo is a clear error and not a bare foreign key failure), and a test reads the source for every kind it names and checks each is a row.

Counts on the header (how many records an import added, replaced or skipped) are left out. The writer cannot count what it never sees (a skipped row), an import records its own summary in `detail`, and the counts of changes made can be counted from the change rows. Whether the header needs them once retention purges change rows (#58) is to be reviewed then. (2026-11-02)

### The CSV parser is a standalone module, and amounts need no number format choice (`northstar/csvparse.py`)
Balance import (#79) reads a file in stages (the file, the column mapping, dates, amounts, then every row), and each stage is a plain function with no database and no web code, so the screens, the dry run and the later locale work (#56) all use the same code. It uses only the standard library `csv` module: the quoting rules are not ours to get wrong. Nothing it reads is logged or kept; an error message may quote a value, and goes only to the person who uploaded it. The file rules (encoding, limits, formats) go into the spec when the import feature ships, not with this module.

Formats are worked out from the data per column, never per row, and the person is asked only when the data cannot decide. Dates can really be ambiguous (`01/02/2026`), so the candidates are listed and the person chooses; a part above 12 or an ISO or dotted column decides it. Dotted dates (`31.10.2026`) are always day first, because the files that write amounts like `1.234,56` write dates that way too. Two-digit years take the most recent year not in the future that ends in those digits, then the usual future-date rule applies to the date. Amounts, however, can never be read two ways: with at most two decimal places, no string that fits more than one of the five number formats means different amounts in them (`1,234` can only be 1234, because as a decimal comma it would have three places). So the number format control #79 proposed is dropped. A column that mixes formats is an error naming the records, and the review shows each amount as parsed. That property depends on `DECIMALS = 2`, which is one constant beside `CURRENCY = "USD"`; a test checks the property over every short string and a second test shows that at three decimals the ambiguity returns, so whoever raises the limit for another currency (v0.3) is told the choice must come back for it.

A file is read whole or not at all: when there is any error there are no rows, and every error is listed with its record number (the header is record 1, a quoted multiline record counts once, blank rows are ignored but keep their number). A column that cannot settle its format is read with the one that fits most of it, so the other problems are listed too and the person is not sent round for each one. A blank cell in a mapped Currency column is an error rather than USD: choosing Ignore for the column is the explicit consent to treat every amount as US dollars, and a blank would be an assumption on the one point the import must not assume. Duplicate dates within the file are left to the dry run. (2026-11-02)

### The import dry run is read-only, stateless, and records the state of every date in the file (`northstar/balance_import.py`)
The Review screen of balance import needs to say exactly what an import would do, and the commit that follows needs to know the account still looks the way the person saw it. The dry run (`plan_import`) classifies each parsed row against the account's live balances as an add, a replace (policy `replace`), an unchanged row (same amount, and the file does not change the note) or a skip (policy `skip`, the default), and lists duplicate dates in the file as errors that name every record involved. A blank note in the file keeps the existing note, so an import can never clear one, and it is never a difference. The account comes only from the entry point, never from the file; a closed account must be reopened first.

It records one expectation for **every** date in the file, not just the dates that would be written: no balance there, or the id and version of the balance there (the version is the id of the operation that last wrote it, 0 for a balance from before the change log, so any later edit changes it). A skipped or unchanged row was classified against the state the person reviewed, so if that balance is edited or deleted before the commit, what would be written no longer matches the review, and the commit refuses the whole import and asks for a fresh review. The cost is an extra "review again" when someone else edits a date that is also in the file. Nothing is stored between the review and the commit: the commit takes the file again with the expectations the review returned and recomputes them with the same function (`expectations_for`), so a forged or empty list can only make it refuse. Imported and replaced balances carry `source = 'csv'`, and a replacement is logged as an update with the old amount, note and source, which is how the change log answers #79's question about the provenance of a replacement. (2026-11-02)

### The import commit refuses unless it is exactly what was reviewed, and otherwise writes all of it (`commit_import`)
The commit is the only step of balance import that writes. It runs in one write transaction, so the plan is recomputed from the balances as they are while the lock is held, and it refuses with `StaleImport`, writing nothing, in two cases. First, if any date in the file is not as the review recorded it: a date filled, a balance edited, deleted or replaced, a version changed, or a date reviewed that is no longer in the file or the reverse. The version is the id of the operation that last wrote a balance, so even several balances written together by one import can be told apart. Second, if the rows, the policy or the account are not the ones that were reviewed, which the expectations alone cannot show, because they describe the account and not the file: the review returns a checksum (a SHA-256 of the account, the policy and the rows) and the commit recomputes it from what it was just given. This matters when a person goes back in the wizard and picks another file or setting and imports without reviewing again. Nothing is stored between the two steps, so a forged or incomplete review can only make the commit refuse.

Everything written is one operation of kind `import`, built inside the commit because its header carries the counts, which are only known after the recompute: the base name of the file, the policy, the date format, the columns used (by position, never header text) and the counts of added, updated, unchanged and skipped. Never anything from inside the file. Written balances carry `source = 'csv'` and share the operation's id as their version, and a replacement is logged with the old and new amount, note and source. An import with nothing to write returns its counts and writes nothing, not even a header. Submitting the same review twice cannot import twice, because the first changes the dates the second expects to be empty. No batch form of the writer was needed: 20,000 inserts with their change rows take under two seconds in one transaction. (2026-11-02)

### One translation from a broken rule to a response, decided by the error's type (`northstar/web/errors.py`)
Six web modules each caught `NotFoundError` and `ValidationError` and turned them into 404 and 422, and the users API chose 404 by looking for "no longer exists" in the message, so rewording a message would have changed a status. ### One rule for asking the server for things: only the newest request counts (`useRequest`, #11)
Some screens ignored an answer that arrived after the person had moved on (the Dashboard, the account chart) and others did not, and each had its own copy of the flag that did it. Now `useLatest` (`frontend/src/useRequest.ts`) is the one place the rule lives: starting a request cancels the one before it (its `AbortSignal` goes to `fetch`) and hands back a ticket, and an answer or an error is shown only while its ticket is current, which also covers an answer that lands before the abort does. A cancelled request is never an error, and leaving the screen cancels the last one. `useRequest(load, deps)` is the hook on top of it for a load that follows the screen's inputs, returning `data`, `error` and `loading`, and every page that loads data uses it. No library: a cache, retries and shared requests are not problems this app has, and the hook has the same shape as the libraries' so one could replace it later. Writes, and the import wizard's commit, are not loads and keep their own busy state.

Two additions to what #11 proposed. `setData` puts in the answer to a change (the server answers most writes with the thing as it now is) and cancels any load still on its way, so an older answer cannot undo the change; without it every page would keep a second copy of its data. And Update balances, whose reads start from a person's action and not from an input, uses `useLatest` directly. Options: `data` is kept while the next request loads, so changing a range does not blank the chart, and `reset` clears it for a screen about one particular thing (an account); `skip` waits for an input that is not known yet. Only `api.ts` calls `fetch`, and a test fails on any `useEffect` that calls a loader, so a new page cannot go back to doing it by hand. (2026-11-02)

### The import routes take JSON with the file as base64, and keep nothing between steps (`northstar/web/import_api.py`, #108)
Three routes under `/api/accounts/{id}/import/` (`read`, `review`, `commit`) expose the parser, the dry run and the commit. Each request carries the file again, because the server stores nothing between steps (see the dry run and commit entries): there is no preview to expire, no upload to clean up and no file kept on the server, and a 2 MB file costs little to send on a home network. The account comes only from the address, so no request model has an account field.

The body is JSON with the file as a base64 string, not multipart. Starlette limits each non-file part of a multipart body to 1 MB, and the `reviewed` value that goes back with the commit has an entry for every date in the file, which is more than 1 MB for a large one. JSON has no such limit and needs no extra parsing, at the cost of a third more bytes for the file. The size is limited while the body is read, to 6 MB (the base64 file, the `reviewed` value and room to spare), so a request that does not say how long it is cannot get round it; both cases answer 413. The parser still refuses a decoded file over 2 MB with its own message.

A problem in the rows is not a failed request: `review` answers 200 with every error listed and nothing that could be committed, and only an unusable file, a bad mapping or a closed or missing account is a 4xx. `commit` repeats every check, since it is given the file again: errors are a 422, and rows or settings other than those reviewed, or an account that moved on, are a 409 naming the dates that changed. The review lists the newest changes first, at most 200 of each outcome that is not "unchanged", with the counts complete and a `hidden` count for the rest, so a 20,000-row file does not put 20,000 rows in the page while the commit still writes and checks every one. `read` works out, for each column, the formats under which every value is a date, so choosing Date for a column needs no further request; a column whose first values are not dates is skipped without reading the rest, which keeps a wide 20,000-row file under half a second. Any signed-in user may import, as for any other balance change. (2026-11-02)

### The import wizard is one page that holds every choice in the browser (`ImportBalances`, #108)
Import is a full page at `/accounts/:id/import` and not a dialog: it has four steps, a list that can hold thousands of rows, and it asks before it is left, which does not suit a box over another page. Every choice (the file, what each column is used as, the date format, the policy) lives in the page's memory, and each step sends the file again, because the server keeps nothing between steps. The steps are not addresses of their own: a reload could not bring the file back, so an address per step would only lead to an empty first screen, and the browser's Back button leaves the wizard (after the same confirmation as any other way of leaving it). Choosing a different file, successfully or not, starts again from the first step, as the spec says; Back keeps everything.

A column has one use and a use is on one column, so choosing Date for a second column moves it and sets the first back to Ignore, and the screen never has a duplicate target to explain. What is worked out from the data is shown as chosen, and only what the data cannot decide is left to the person: the date format when more than one fits (the choices are only the formats that fit; the screen cannot continue until one is picked), and nothing for amounts. When no format fits any value the person may continue, because the review then lists the values that are wrong, which is more use than a blocked button. The three loads (the account, the file's columns and the review) go through `useRequest`, so an old answer after a quick change of policy is ignored, and the commit is not a load: it has its own busy state and cannot be pressed twice.

When the commit answers 409 the page asks for the review again and shows the server's message, which names the dates, with those rows marked "changed", and the person looks at an up-to-date review and presses Import again; nothing is retried on their behalf. Any other failure says nothing was saved and keeps the review. Import CSV… is offered only for an open account, on the account page and in the Accounts list's menu, and the page itself says to reopen a closed account. The review says importing cannot be undone, until undo (#81) lands and the line is removed. Known limit: duplicate dates in the file are found only once every row reads, so a file with other problems as well shows the duplicates on the second try (the parser returns no rows when any row fails).

The way out is a button of the wizard, not part of the step pills: a red Cancel on the first three screens (beside Choose file… on the first, and first in the bar of Back and Continue or Import on the others, so it stays at the same place when the main button's label changes width) and Exit on the result, which replaces the link back to the account. Both do what the browser's Back button does, because the page may have been opened from the account page or from the Accounts list and the person expects to return to where they were. The router therefore keeps each history entry's position among the app's own pages in the entry's state (`history.length` also counts other sites, so it cannot say whether there is a page of the app to go back to) and `goBack(fallback)` goes to the account when there is none, as in a new tab. It asks the leave guard once itself and tells the browser's popstate not to ask again, which would otherwise ask twice, and it is the only way out that does not leave an extra history entry when the person stays. Red is for Cancel because it throws away the file and the choices, and the leave prompt covers a slip. After the import is written there is nothing to cancel, so the same place offers Exit, in the normal button color, since a red Cancel there would read as undoing a saved import. (2026-11-02)

### Export is one account, four columns, and a plain download (`balance_export`, #80)
The first export is deliberately small. It writes one account's balances with `Account ID`, `Account Name`, `Balance Date` and `Balance Amount`, oldest first, and the browser saves it with no questions. An export of every account in one file, and the notes, sources and currencies, are left for later: nothing in this file stops them being added, and the import ignores columns it does not use.

The import already prefilled a column named "balance date" as the date, and "balance amount" was added to the names it knows for the balance, so an export read back into the same account needs no mapping and reports every date unchanged. That is tested by importing the export, not by comparing header lists. Amounts are written from integer cents with integer arithmetic, so there is no floating point to round, and the sign is kept as stored, as the import reads it.

It is a `GET` that answers with an attachment, and the buttons set `window.location`, so no script reads or holds the file. Any signed-in user may export, since it is read-only and shows what they can already see. A closed account can be exported because nothing about it changes. One file is one account because import is one account: a file with several accounts would be silently written into whichever account the person imported it into. When every account is exported the Account ID column is what a multi-account import would read.

An account name that starts with `=`, `+`, `-` or `@` is written as it is, so a spreadsheet may read it as a formula. The name is only there to be read, and changing it would stop a file matching its account. Revisit if exports start to be opened in spreadsheets by people other than the household. (2026-11-02)

### The imports register is read from the change log, and the import's header names the account (`import_register`, #81)
The register of past imports needs no table of its own. Every import that writes something is one `sys_operations` row of kind `import`, whose header already holds the file's base name, the policy, the columns and the counts, with the time and the user on the row. One field is added to that header, `account_id`: without it the account could only be found through the balances the import wrote, which fails for an import that only replaced balances (a replace logs the changed fields, and the account is not one) and for balances deleted later. No migration, because the header is JSON, and no import exists outside throwaway test databases, so no header lacks it; one that did would list as "Unknown account".

The page is admin only, in the route and in the app, because import is. It lists the newest 25 and says when there are more, with no paging, since imports are rare and 25 is a lot; a page of older ones is cheap to add if it is ever needed. The date is the UTC date of the operation, as everywhere until the timezone work. A deleted user still shows by name, because the register reads the users table and not the view of live users. The account is shown as it is now, and a deleted one as "(deleted account)", so a rename follows the account and a deletion does not make a row vanish. "Reverted on" is read from an `undo` operation pointing at the import, which nothing creates yet: the column exists so the undo that follows changes the page by one button. (2026-11-02)

### Undo is all or nothing, for imports only, and checks each balance's version (`import_register.undo_import`, #81)
An admin can undo an import from the Imports page. It deletes the balances the import added and puts back the amount, note and source of the ones it replaced, and only if every one of them is still as the import left it: the balance exists, its `version` is still the import's operation id (nothing has written it since, whether an edit, a later import or another undo), and its account is open. Otherwise it is refused with a 409, writes nothing and names up to 10 dates with a reason each. This is the design's "never overwrite a later change" without its partial undo: no skip list, no per-record savepoints, no preview that runs the inverses, no confirmation bound to a plan, and no "a partial undo is final". The fuller design is kept in `docs/design/undo` for the history screens (#58), and nothing stored would change to add it. Fixing a few balances by hand and trying again was judged better than a rule about what a partial undo leaves behind.

An import writes only inserts and replacements, never moves a date and never deletes, so the date-move ordering and the re-insert case of the fuller design do not arise. A replacement logs only the fields it changed, so the old values to restore are those in the change row, and the date of a balance that has since been deleted is found from the log, where its delete (or its insert) kept it.

The plan is a `GET` that writes nothing and the undo is a `POST` that runs the same checks again inside the write transaction, which is what makes the dialog's answer safe to rely on: the one case it cannot promise is a change made between the two, and that is a refusal. The undo is one `undo` operation whose `undoes_operation_id` is the import's id (the unique index keeps it to one), and the writer's `Operation` gains an optional `undoes` for it. Each restored balance takes the undo's id as its version, so a later undo of anything older cannot match it. A closed account is refused because the balance functions refuse changes to one, and a deleted account because its balances are not in any view. Imports in the wizard now say they can be undone from the Imports page. (2026-11-02)

### A balance's version is the token for conflicting edits, and the check comes first (`balances.require_version`, #10)
Two people editing the same balance used to mean the second save silently replaced the first. The page now sends back the `version` it loaded (the id of the operation that last wrote the balance, already on every balance since the change log) and the server refuses with a 409 if it has moved. The issue proposed `updated_at`, which has one-second resolution and would miss two edits in one second; the version has no such gap, and it also says who: the operation that wrote it names the user and the date, so a refusal can say "changed by Sam Example on Nov 2, 2026" and the person knows whether to expect it. A deleted balance is found from the change log, where its delete kept its account, date and who.

The check runs before anything else, even when the new values equal the current ones, so the rule is one sentence that never depends on the values (two people entering the same number still see that the balance moved). It runs inside the write transaction, so a change cannot slip between the check and the write, shown by a test in which a second request waits for the first. Deleting is checked as well as editing, and a blank date on the Update screen is checked as "none": a balance added since is a refusal, as on the import review. Rows the Update screen did not send (left alone, or typed as the amount already saved) are never checked.

On the Update screen a refusal saves nothing, reloads the date, keeps what was typed and marks the rows that moved on, so pressing Save again sends the newer versions and replaces them knowingly: the person has seen what changed. The edit dialog offers "Use the current value", which drops the typed values, because merging two edits to one amount is not something the app can do for the person. The page behind a dialog is refreshed in place and not reloaded, since a reload blanks the page and closes the dialog.

The plain functions take the version as an optional argument and leave the check out when it is not given (scripts and tests have nothing loaded), but every web route requires it, so a client that forgets is refused with a 422 and not silently unchecked. The Add a balance form is unchanged: a date that already has a balance is replaced there by design, and a page that has not loaded that date has no version to send. (2026-11-02)

### The sign-in page is a page of the React app, and the app's files are public (#65)
The spec used to say the sign-in page was rendered by the server "because the app itself cannot be public", and no reason for it was recorded. The build holds the app's code and no data, and every endpoint that returns data needs a session, so serving the files to a signed-out visitor shows them the screens' structure and nothing else. That is the usual arrangement for a React app with a cookie session, and it removes the second way of building a page: one bundle, one router, and the sign-in page can share the theme, the components and (later) the brand mark and the first-run page.

The public paths are now `/login`, `/api/auth/login`, `/assets/*` and `/static/*`, in one list in `app.py`. Everything else, including `POST /api/auth/logout`, still needs a session. The server still redirects an unauthenticated page request to `/login?next=…`, so there is no flash of the app and no client-side guard to keep in step with the server's list of pages. The sign-in page itself does not ask who is signed in, which would send a signed-out visitor straight back to it.

`POST /api/auth/login` takes JSON and answers JSON. Throttling, the wrong-password message, `Retry-After`, the cookie flags and `safe_next` are unchanged and stay on the server: the answer carries the address to go to, already checked, and the page leaves with a full page load, so the app starts clean with the new session, as sign-out already does. `/login` and `/logout` as form posts are gone, and `logout` is no longer a reserved name.

Signing in no longer works without JavaScript, which is not a loss since nothing after it does. `jinja2` and `python-multipart` were only used by the old page and its form, so they are no longer dependencies.

### System properties are named text values checked by their data type and by validators their feature supplies (`northstar/system_properties.py`, #124)
One table, `system_properties`, holds the settings for the whole installation, and one function, `set_property`, is the only way a value is written. It is not a `sys_` table: the spec reserves that prefix for tables the application writes for itself without audit columns, and admins edit this one, so it has the audit columns and its changes go in the change log. Its id is an integer, because `sys_record_changes.record_id` is an integer and a text name could not be logged; the name is a unique key the code uses.

A name is lowercase dotted segments (`currency.exchangerate.staleness_days`) and the first segment is the group the page lists it under, so there is no category table to keep in step with the names. A value is always text and is checked by its data type: String (256 characters at most), Integer (a whole number JavaScript represents exactly) or Lookup (one of at most 20 rows of `ref_property_lookups`). A list that is long or comes from another table is a String with a validator and not a Lookup, so a Lookup never reads a table named in data and nothing stores SQL.

What a feature requires beyond the type is a validator: a plain function with no side effects that gets the property's name, the typed current and proposed values, the actor and the open connection, and either raises an error text or accepts, optionally locking the property. The validators of a property are rows in `ref_property_validators`, naming functions in one explicit mapping, `VALIDATORS`, in order. The data says which properties have rules and the code says what they enforce, so the rule is visible in the database without storing an expression in a column. The setting service runs the type checks and then the validators in one write transaction and raises the first refusal unchanged, so a value its feature could not use is refused when it is saved and not found later in an unrelated operation. A name that is not in the mapping refuses the change and is logged. A submission equal to the stored value writes nothing and runs no validator, so a stored value can always be saved again after a rule is tightened, at the cost that it is not flagged until someone changes it.

`allow_null` says whether a value may be set back to unset, and a blank submission means unset because empty text is never stored. `read_only` is data, set by a migration or by a validator's decision to lock in the same audited write, and never by an admin. There is no version check for two admins saving the same property: the later valid save wins and the change log shows both.

The three `ref_` tables are loaded by migrations and never written at run time, so they have no audit columns, are not in `sys_audited_fields`, and the writer refuses them. `account_classes` is the same kind of table but predates the prefix, and renaming it would rebuild a released table for no gain. A property is added by the feature that reads it, with its hint and validators in the same migration; the first three are `ui.theme.default`, `balance.stale` and `system.currency`. The first two are read where a default used to be fixed in code: `users.add_user` takes a new or reactivated user's theme from `ui.theme.default` (the schema's own default of dark is now only a fallback for a row written some other way), and the Add type form starts a new account type at `balance.stale` through the types list, so the starting 35 is the same as before but an admin can now change it. `system.currency` is read by nothing yet, and becomes the permanent system currency with the catalog. (2026-11-04)


### The currency catalog, the account currency and the system currency (`northstar/currencies.py`, #125)
The catalog is one table, `currencies`, and not a read-only `ref_` table beside a list of enabled ones, because an admin will switch `is_enabled` at run time and an ordinary household table gets its audit columns and change log for that. Accounts point at its integer id, as they do at account types. Its rows come from the published ISO 4217 "list one" file (SIX, 2026-09-17): the currencies that are not funds and have 0, 2 or 3 minor units, 155 of them, with ISO's names unchanged. The two 4-decimal codes are funds, so the `CHECK` has no room for four. Names are ISO's and short, so the search box finds "Yen" but not "Japan"; a country column can be added later if that proves annoying. A currency is never deleted and never changes its code or precision (triggers), because that would silently change what every stored balance means. The trigger does not look at accounts, so a later rebuild of `accounts` need not drop it.

`amount_cents` is not renamed. It holds integers in the minor unit of the account's currency. SQLite has no decimal type and sums integers exactly in the database, and a rename would touch every query for no change in meaning. The spec, `docs/schema.md` and the comments say "minor units".

The system currency is the property `system.currency` and not a second place: a String with the validator `catalog_currency`, which accepts only a catalog code, refuses a change once any account exists (deleted ones count, because they keep their currency) and locks the property in the same audited write. That is the "accept and lock" decision the setting service already had, used for the first time. An existing installation with an account is USD and locked, because every amount it holds is a dollar amount. One without is unset, the migration leaving the property unset although `allow_null` is 0, which the service allows for a property created that way. While it is unset the server refuses to create an account (a ValidationError from `add_account`, so the page and the API agree), and the Add account dialog says so and sends an admin to the page that sets it.

Enabling a currency is not built. The net worth sums `amount_cents` across accounts, and conversion arrives with exchange rates, so enabling a foreign currency earlier would add euros to dollars. The `is_enabled` column and the rule that an account's currency must be usable (the system currency or an enabled one) are in place and tested; nothing sets the column, so every account is in the system currency until rates exist. The interface is single-currency without a stored flag: there is no currency field while only the system currency can be chosen.

Amounts are parsed in the account's own digits and refused, never rounded, when they have more. The ceiling stays 9,999,999,999,999 minor units for every currency, which is inside what JavaScript represents exactly. Until locale-aware formatting arrives the interface shows dollars as `$1,234.56` and any other currency with its code. The importer still reads two decimal places, so it refuses an account whose currency has another precision, and the export already writes the account's digits. The system currency's search box is the browser's own `<datalist>` over the catalog: no new component, no dependency, and the server checks the code against the catalog. (2026-11-04)


### The Currencies page is a plain, read-only list of the table (#141)
Admins get a page listing the `currencies` table with the number of live accounts in each, because the catalog was otherwise reachable only through the System properties search box. It shows the stored values and nothing derived. In particular it does not know the system currency: no tag, no filter, and the Enabled column is the `is_enabled` flag as it is, so the system currency reads No unless something enables it. A column that merged "enabled" with "is the system currency" would show a value that is not in the data and would make the page depend on a setting it has no other use for. The cost is that a hint such as "usable when enabled" is slightly untrue of the system currency, which the page leaves unsaid.

The page changes nothing. The enable control, links from a row to its rates and the Add Currency wizard arrive with exchange rates (#130, #131), which will build on this list. The count includes closed accounts, which still hold a currency, and leaves out deleted ones, as every other count does. Search matches a code that starts with the text or a name that contains it, so "sd" does not find USD. The filters (all, in use, enabled) and the search run in the browser over the whole list, which is 155 rows. (2026-11-05)


### Locale: a catalog of conventions we own, generated from CLDR, read from the database (`northstar/locales.py`, #126)
How numbers and dates are shown and typed is a person's locale, and the conventions are rows of a read-only table, `ref_locales`, not the browser's `Intl`. Browsers carry different CLDR versions and write some marks differently (Node writes the Swiss group mark as `'`, U+0027, where CLDR has `’`, U+2019), and the server has to read exactly what the page shows, so one table that both sides read cannot disagree. The rows are generated by `scripts/generate_locales.py` from CLDR through Babel and committed as a reviewed migration, as the currency catalog was built from ISO. The database table is the only runtime source: there is no second JSON copy, nothing at run time reads CLDR, and Babel is a development dependency that is not in the image. The tag is the primary key, unlike the integer ids of the other `ref_` tables, because it is already the identifier in preferences and the API and shipped tags are stable. The table has no column for what is fixed: groups of three, grouping from four digits and an ASCII minus are application rules, documented and tested once, and the generator refuses a locale that goes beyond them (it also probes Node's `Intl`, because Babel cannot see CLDR's minimum-grouping rule) instead of fitting it into the model. Adding a locale is therefore a checked change and not only a row.

The default for new users is the String property `ui.locale.default` with a `catalog_locale` validator and no `ref_property_lookups` rows, so the catalog stays the single list, as the earlier decision about lists that come from another table says. `users.locale` is a foreign key to the catalog as well. Both are intentional: one lives in a generic property table and the other in a dedicated column, so they are enforced by different mechanisms. SQLite refuses to add a `REFERENCES` column with a non-null default while foreign keys are enforced, so the migration runs in the `-- northstar: rebuild` mode, which turns enforcement off and checks the keys again before it commits. A new or reactivated user takes the current default, as the theme does, and an active user is never changed by it.

Typed amounts are read with the person's locale and never another one, which is a narrower promise than refusing everything ambiguous: `1.234` is grouped 1234 in German. The look-alikes of the group mark (spaces, apostrophes) are normalised only for the matching mark, and arbitrary whitespace is no longer removed, so `1 2` is now refused where it used to be read as 12. Display, editable text and the canonical export are three separate formats. Only editable text must read back exactly, because display includes a currency code that the parser does not accept. Dates are formatted by filling the locale's template from the `YYYY-MM-DD` text, so the frontend still never creates a JavaScript `Date`; `Intl.DateTimeFormat` would need one, and its text varies by browser. Month names stay English because the interface does. The page waits for `/api/me` before it draws anything signed in, with a retry, so a form is never started under an assumed locale (this also removes the brief wrong currency symbol before the currency loaded). (2026-11-05)


### Choosing a locale, reading amounts as they are typed, and refusing a save made under a format that has changed (#127)
A person's format is a select in the profile's Appearance panel, beside the theme, and like the theme it saves as soon as it is chosen, with no Save button and no hint text. The admin's new-user form has the same select, starting at the system default, which `GET /api/me/locales` returns with the list so that an ordinary user and the form read one source. A user added through the API with no choice still gets the default. A reactivated user takes the choice made on the form, which starts at the default, so the rule that a reactivated user takes the current default holds for every caller that names nothing.

Under every amount box a line says how what is typed reads, or why it cannot be, in the server's own words (the frontend keeps the messages in step with `parse_amount`, and the shared vectors check that every refusal says the same thing in both). It is empty until something is typed, so a form is never noisy at rest. It is there so a person finds out before saving, not after the balance is committed, which is where the promise that a locale is read in the person's own conventions and never guessed needs it most: `1.234` is 1234 in German, and the line says so.

A save made under a format that is no longer the saved one is refused with a 409 that names the new format and writes nothing. The page sends the tag of the format it is using, which changes only when the page loads the person's details again (on sign-in, after a profile change, or after this refusal), so it is the format the draft was typed in. The server checks it before it reads the amount, so a draft that is also malformed is told about the format and not the amount, and checks it again inside the write transaction, so the preference cannot change between the check and the write; a test removes the early check and shows the second one still refuses. The page keeps the draft and asks the shell to load the new format through a context, rather than any page loading it itself, so there is one place that reads `/api/me`. The draft is then read in the new format, and the reading line shows how, which is better than converting it: the page cannot know what the person meant. On the Update balances screen, the boxes that still hold what was loaded are written again in the new format and what was typed is left alone. Nothing is checked when no amount was typed, and a caller that names no format (the command line, a script) is not checked. (2026-11-05)


### Messages say dates and numbers in the person's locale, with the locale set once per request (#127)
The rule is that every message written for a person respects their locale, not only the screens. Two sentences the server writes named a date as ISO text ("There is already a balance on 2026-01-31", and the duplicate dates in an import file), and so did the reasons an import cannot be undone, and counts of a thousand or more were grouped with US marks or not at all. The page cannot reformat text inside a server sentence, so the server writes it by the same template. The messages are raised deep in the rules, where there is no user and no connection to ask, and threading a locale through every function that can refuse would touch most of the application, so a request sets the signed-in person's locale in a context variable once, in `run`, and a message reads it with `locales.speaking()`. A new message gets the right format by using `speaking()` and nothing else. Outside a request it is US English, which is what the command line and the tests read, so no existing caller changes. It is a context variable, not a global, so two requests at once never see each other's locale. Dates in data fields stay ISO, because the page formats them and a person never reads them raw. A test per kind of message checks the format in several locales, and the shared vectors for dates and whole numbers are read by the server's tests too. (2026-11-05)


### Balance imports use the account currency and an inline number-style choice (#128)
The account supplies currency and precision to file detection, review and commit. Currency is no longer a column mapping, and symbols do not block a file or select its currency. The review explicitly names the destination currency; importing into the wrong account remains the person's error, but the review says so when the file itself says another currency: a Currency column naming one, or an amount with a euro or pound sign that is not the account's. The note does not block, because the person may know better, and nothing is converted. A dollar sign and a yen sign name no currency, each being shared by several, so they never raise it. This changes only import handling: export code, columns and validation are outside #128. The chosen number format is included in new import audit metadata, while undo continues to use recorded changes and can undo older imports without that metadata. No schema migration or dependency is needed.

The precision of the account's currency has no default anywhere in the file readers (`parse_file`, `parse_amount`, `detect_number_formats`), so a caller that forgets it fails with an error and cannot read a whole-yen file as cents. ### Exchange rates, conversion and the currency page (#130)
Each currency has an admin page, opened from its name on the Currencies list, and the list became read-only again: the Enabled switch, the date rates start from and the rates themselves live on the page. Enabling saves at once in both directions with no confirmation, because disabling deletes nothing and is undone by switching on again. An Add Currency wizard is not built. What it was to decide (when rates start, switching on) is on the page, and #131 adds the rate source and "fetch rates from" there. Rates are entered after a currency is enabled, and a new account in another currency needs at least one stored rate, which is the guard that keeps a net worth from adding amounts in different currencies. The system currency is always enabled, set by the same write that saves it and by a migration on an existing installation, so "usable" is simply "enabled".

A rate is a row of `exchange_rates`: 1 unit of the currency = `rate` units of the system currency on a date, unique on (currency, date). The rate is the text of an exact decimal (digits and a point, at most 12 significant digits), because SQLite has no decimal type, `REAL` is floating point, and a fixed integer scale chosen now could not be widened without a migration. The table has an integer `id` and a unique pair and not a composite key, because the writer and the change log address rows by id. Triggers refuse deleting a rate and changing its currency or date: a correction changes the value and makes the source manual.

Conversion is exact and is done in Python (`networth.convert`): `round_half_away_from_zero(amount x rate x 10^q / 10^p)` for each account on its own, then summed. SQLite cannot do it: a 10^13 amount times a scaled rate overflows 64 bits, and SQLite then turns the result into a float without saying so. A view, `account_days`, does only the lookup, one row for every day and account from the first balance to the newest balance or rate. A view cannot call `clock.today()` and SQLite's `'now'` is UTC, so the calendar stops at the newest balance or rate and a later date is answered with the last day, which is the same answer because nothing changes after it. The view reads `live_accounts` and `balances`, so anything that rebuilds either must drop and create it too. Zero balances need no rule: a zero converts like any amount and needs a rate.

A date on which an account has no rate has no net worth and is refused with the currencies named, and a series is never a partial total. The uncovered dates are not always a prefix, as the first design said: a euro account that begins in March with euro rates from May leaves only March and April uncovered, and January and February before the account are fine. So a series starts at the first date from which every later date can be converted, says where it starts and which currencies lack a rate before then, and is empty with that explanation when no date can. One account's views are in its own currency and have no coverage rule. A currency's `rates_start` is an intent that the page compares with the first stored rate and does not enforce, because the coverage rule already says what can and cannot be shown. System properties gain a Date type, `currency.rate.stale_days` (14) and `currency.rate.start.default` (2000-01-01). A warning on balance entry for a date before a currency's rates start was left out and can be added if it is missed. (2026-11-06)

### An account is shown in its own currency everywhere, with a Currency column (#149)
Creating and showing accounts in other currencies adds no new rule, only the places where the account's currency is used. The Add account dialog offers a Currency box when a currency other than the system currency can be used, and the server's own rule is the same list: the system currency, or one that is enabled and has at least one stored rate (`currencies.choosable`). The API takes an optional currency code and the opening balance is read in it, in the same all-or-nothing write. Every account row and page carries its currency, so the frontend formats an amount with the account's currency and never with the system currency except for totals, which are converted by the server. A balance in conflict carries its currency too, because its message writes the amount. The Accounts list and the Update balances screen got a Currency column and not a code beside each foreign amount, so a dollar account shows USD as well: one rule, no special case. The amount still carries its code as the app writes every amount (`EUR 10,000.00`). A foreign account's worth in the system currency is not shown on its page or in the list, and is left to the v0.5 household reporting. (2026-11-06)

### The installation's time zone is a system property, and `now()` stays UTC (#152)
The container ran in UTC unless an operator remembered to set `TZ`, so "today" could be a day off for the household for part of every evening, and a scheduler needs to know the household's day. `system.timezone` is a String system property holding an IANA name, checked against the zone database by the `iana_timezone` validator, empty meaning UTC. `clock.today()` is the date of `clock.now()` in that zone. The zone is held in the clock module, set at startup and when the property is saved (after the change has committed, so a refused or rolled-back save changes nothing), so `today()` needs no database and tests still fix it in one place. That is correct for one process, which is what the image runs. `TZ` is kept only as the first-start default: while the property is empty and `TZ` names a zone it is copied in once, by the system user, and then ignored, with a warning when they differ. A `TZ` that is not a zone, or a stored name this machine has no zone data for, is logged and UTC is used. `now()` stays an absolute UTC instant, not a local time, because sign-in throttling subtracts durations from it and a local time is wrong across a daylight-saving change. Changing the zone moves where "today" begins by at most a day and changes no stored date, because balances and rates are calendar dates. The image has the zone database, so the application needs no `tzdata` package. Windows has none, so the tests that use a zone name get it from `tzdata`, a development-only dependency. The dates in the frontend are still strings and it still never creates a `Date`. (2026-11-06)

### The scheduler is built in, with a lock whose holder cannot commit once its lease has run out (#138)
The rate fetch needs a daily job with nothing set up on the host, and SimpleFIN will add more, so the application has a small scheduler: a registry of jobs in code, a daemon thread that calls one function, `run_due`, about once a minute, and two `sys_` tables, `sys_jobs` (one lock per job) and `sys_job_runs` (every run). No library: the loop, the registry and the tables are small, and a library's job store would duplicate the tables the lock and the history need. Reconsider if schedules become cron expressions or there are more than about five jobs. The start time of a job is a Time system property and not a column, so it is edited, validated and audited on the System properties page like any setting. The registry is the catalog, and the database holds only what changes at run time, seeded from the registry at startup. A lease cannot promise that two executions never overlap, because a paused process can outlast it. So the guarantee is that a stale owner cannot commit: a lock has a fresh token for each acquisition, and each batch a job commits and its final outcome write start with one statement that checks the token and the unexpired lease in the same transaction, which is also the renewal. Fetching outside the database may overlap, which is harmless. A run is claimed in one transaction, taking the lock and inserting the run row, and a unique index on (job, run date) for scheduled runs makes it once per date. That is at most one scheduled claim a day, not guaranteed completion: a crash after the claim loses that date's scheduled attempt, which is accepted, because the next date runs normally and the command line (#131) is the manual repair. Expired locks are cleared, and their running rows marked abandoned, by a reconciliation that is the first step of every tick, so abandonment is recorded at the first reconciliation after the lease expires. Each decision rereads the clock and takes the zone and the start time in one snapshot, so a job that crosses midnight does not leave the next one judged on yesterday. A job fails with a category and a message written in our own code, and the text of an exception is never logged or stored, because it can carry a request URL with a credential: an unexpected exception is recorded as its class and the place it was raised. A failing tick is caught, logged once per kind and retried with a growing pause up to five minutes, so the thread never ends. The lease, the retry pauses, the call timeouts, the tick, the join and the 90-day retention are constants and not system properties: they depend on each other, a wrong value gives overlapping or abandoned runs and not a slower scheduler, and nobody could see the effect of changing the retention before a Jobs screen exists. A job's deadline and retry pauses belong to the job in the registry. A manual run from a screen (queued, returning a run id) and the Jobs screen are deferred to #154 and #155, so the table has the `started_by` value `manual` for the command line but no `queued` outcome. The column that says who started a run is `started_by`, not `trigger`, which is an SQL keyword. (2026-11-06)

### Rates come from Frankfurter, once a day, insert-only, in spans of a year (#131)
The rate fetch is the first job of the in-app scheduler, with its start time in the Time system property `currency.rate.fetch_time` (18:00 in the installation's zone, empty meaning off). Frankfurter was checked against its documentation and its live API on November 6, 2026: `base` the foreign currency and `quotes` the system currency gives 1 unit of the currency in the system currency, which is the stored direction, so nothing is inverted. Its time of day for publication, its rate-limit figure, its attribution and the public API's terms are not stated, and none was guessed: the 18:00 default is a choice, and a late run only delays a rate by a day because the next run fills what is missing. The page names Frankfurter as the source of a provider rate, which costs nothing and covers attribution. The fetch is insert-only, as designed: a date that has a rate is never changed, so a rate an admin typed or corrected survives. It stores every day the provider returns up to today, weekends included, because the provider carries Friday's rate over the weekend and the lookup is the latest rate on or before a day, so the extra rows change no result and no rule has to guess which days are real; the cost is about 9,800 rows a currency from 2000. A date after today is dropped, because the provider answers with the weekend ahead and Northstar stores no rate dated after today. What is missing is found from the rates the provider has supplied, not from a last-run value: the days after the newest of them, and once the days from the rates start to the day before the oldest of them, starting no earlier than the provider's own first date for that currency, so a currency whose history begins late is not asked for its empty past every day. A range is asked for in spans of at most 366 days, newest first, because one call for 26 years of one currency took 22 seconds and 618 KB; each span is checked whole and committed on its own, and a span that fails stops that currency, which is why a stored range never has a hole inside it. A bad span is rejected whole and the currency named in the failure after the others have been fetched and kept, a provider that does not answer or is busy is retried by the scheduler, which repeats the whole job and finds its place again, and nothing the provider says is logged or kept. Numbers are read as the provider's own text, never as floats, and checked by the same rule as a typed rate. The standard library makes the request, so there is no new dependency, and the provider's address is a constant because a setting for it would be a setting nobody needs until someone self-hosts. Scheduled rates are an operation of a new kind, `scheduled`, made by the system user, and each rate is in the change log like any other insert. The command line `python -m northstar.rates fetch` is the manual run and the Fetch now button is not built (#154). The currency page's Rate source block says when the fetch runs and how the last run went, with no counts by currency, because the run record holds only a message. (2026-11-06)

Found by running the fetch in the UAT container against the real provider, which the fake provider in the tests had not shown, and corrected in the same pull request. First, where Frankfurter's history is sparse (Armenian dram before 2011 has no weekends and gaps) a request that starts on a day with no observation also answers with the last observation before it (a span from 2009-10-25 came back with 2009-10-24). Rejecting the span for that made the backfill of that currency fail every day, so a date outside the span is dropped, as a date after today already was: it belongs to the neighbouring span. Second, the edges of what has been fetched were the oldest and newest stored rates, so a rate an admin had typed at the start date made a half-fetched history look complete and left a hole in the middle that no later run would fill, against the rule that a stored range has no hole. Only a provider rate is now an edge, and a typed or corrected rate is still never overwritten.


### First-run setup is a page with a token from the log, one transaction and its state in memory (#64)
This replaces the command line as the way to make the first admin (the decision at the top of this file about passwords on a prompt still holds for `set-password`). The command needed a shell on the host and could not set the system currency, which must be chosen before the first account and never changes, so a new installation had a gap between the first sign-in and a usable app. The page makes the first admin and the three settings that matter in one pass, so there is no state in which an administrator exists and the installation is half configured. The full design is `docs/design/first-run-setup.md`.

The page is unauthenticated and creates an admin, so it is guarded by a random token that startup prints once in the container log. Printing it is the one deliberate exception to never logging a credential: the person who can read that log already owns the machine, and the token only lets someone create the first administrator. It is entered in the page, never put in an address, and grants a setup session in an `HttpOnly` cookie that is valid only for `/api/setup`. Setup is open while no administrator row exists, deleted ones included, so deleting an administrator cannot reopen a way to create one. That counts the rows that remain, not a record that setup once ran, and a database restored with no administrator is the separate recovery feature (#158).

The token, the setup sessions and the count of wrong tokens are held in memory, not in the database. The behaviour that was agreed (a restart makes a new token and ends every session, a session lasts 30 minutes) is what memory gives for nothing, and it needs no migration and leaves no stale rows to clean up. It is correct for one process, which is what the image runs (no `--workers`), the same assumption the clock's zone makes. With several workers each would have its own token and only one would be printed, so reconsider if the image ever runs more than one. The wrong-token limit (5 in 15 minutes per address) is a plain in-memory window and does not use `sys_login_attempts`, which is about emails. Behind a proxy that is not trusted every visitor shares one count, which is acceptable here: the token has 256 bits, the window is short and a restart clears it.

The administrator and the properties are one `write_transaction`. The administrator is made by the system user, because nobody is signed in, through `add_user`, which gives them the chosen locale directly instead of copying the default that is about to change. The properties are saved by the new administrator through `save_property`, which is the body of `set_property` without its last step. That step sets the clock's zone, and the clock is process-wide, so it must happen after the commit and not for a save that is rolled back. Going through the setting service keeps its validation, the currency lock and the no-write rule for an unchanged value, so setup has no path around them. Both use the operation kind `ui_edit`: a new kind is a row in `sys_operation_kinds`, which is a migration, for no gain, and the actor already says who it was. Every field's refusal is gathered and reported together, and the transaction is rolled back whole. Hashing the password happens under the write lock, which `add_user` otherwise avoids, once, while nobody else has anything to write.

An email that belongs to any user, a deleted one included, is refused, because `add_user` would reactivate that person and setup must never promote anyone. Setup does not sign the administrator in: the person types the password they just chose, which keeps one way to start a session and proves it was saved. The page leaves the email in the browser's session storage for the sign-in page to fill in, never in the address, and never a password.

`users create` is removed and `set-password` and `list` stay, so there is no second way to make an administrator that skips the guard. The plan called the kept command `reset-password`, which was never its name.

### OIDC settings are properties with guards, a Boolean type, and a host command to get back in (#166)

OIDC sign-in is configured as ordinary system properties, so it uses the same service, validators and change log as everything else, and the client secret is the one thing that is not: it comes from the environment (a file, or a variable) so it never reaches the database, the change log or an API response. `NORTHSTAR_PUBLIC_URL` is an environment setting because the callback address registered with the provider must not depend on request headers.

A Boolean is a new data type, not a Lookup of two options. It is stored as `true` or `false`, but `get_value` returns a real `bool`, one rule refuses anything else for every Boolean, and no option rows are needed per property. It is edited as a Yes or No dropdown, which is the editor's existing select, so there is no new CSS.

The validators exist to make a lock-out impossible to save: OIDC on needs everything it uses, OIDC off needs password sign-in on, and password sign-in off needs OIDC on and an admin who has already signed in through it. The last of these asks whether an active admin is linked to the issuer, which needs the identity storage of the next step. Until then that check is a function that answers no, so password sign-in cannot yet be switched off. That is the safe direction, and step 2 (#167) replaces the function. The session lifetime is bounded to a year (8,760 hours) because a larger number could only overflow the expiry date. Plain `http://` is accepted for the public address and the issuer only on a local host, for trying Northstar out on one machine. The way back in is `python -m northstar.signin enable-local`, in its own small module because it is about sign-in settings and not about users. It writes through the setting service as the system user with the `cli` kind, needs only the database file, and works with no provider and no session.


### An OIDC identity is a household table, resolved in one transaction, and a user with no password is refused like an unknown email (#167)

`user_identities` is a household table with audit columns and not a `sys_` table. A binding is a durable fact that ties a person to a user and outlives every session, so it belongs in the change log, with who made it and when (the system user, in an operation of kind `oidc` that says whether it created a user or linked one). Triggers refuse deleting or changing a binding, because replacing one must be a deliberate administrative procedure and not a side effect. A user is only ever marked deleted, so the binding stays and a later sign-in under the same identity, or the same email under a new subject, is refused instead of bringing the person back.

`sign_in` resolves the claims and starts the session in one write transaction, reading the configuration inside it, so a refusal leaves nothing behind and a setting that has just been changed is the one that counts. Two first sign-ins at once make one user and one binding, because the second waits for the lock and then finds the identity known. Two different subjects with one email never merge: the first binds, and the second is refused, which the explicit check and the unique index on `(user_id, issuer)` both enforce. A refusal carries a code and a reason for the log that never holds a claim, an address or a token, and one message covers the cases a stranger must not tell apart.

A user "has no password" when their stored hash is not a well-formed scrypt hash. That is the marker the system user and deleted users already have, so no new column is needed and nothing can match it. Password sign-in used to return at once for such a row, which would have shown that an account exists with no password, because an unknown email costs a whole hash. `authenticate` now treats a row with no usable password like an unknown email and spends the same hash on the dummy one. The session's method and fingerprint are columns on `sys_sessions` with a trigger that pairs them, because a table check cannot be added to an existing table. The fingerprint hashes the issuer and the client ID as a JSON array, so no choice of the two can run into another. The step-1 check that an admin has signed in through OIDC before password sign-in is switched off is now a query for an active admin bound to the configured issuer. The login-transaction table is created here with the columns the design needs, and the next step may change it with a migration if the flow needs something else.


### The OIDC flow uses joserfc and the standard library, and every failure is one of a few fixed codes (#168)

The flow is written out in `northstar/oidc.py` on `joserfc` (token and key handling) and `cryptography`, with the standard library for the HTTP requests, and not on Authlib. Authlib's `authlib.jose` is deprecated in favour of joserfc, its client needs a session middleware and `httpx2` that this app has no other use for, and an OIDC client for one provider is a few hundred lines whose every rule is then in view and tested. joserfc refuses `none`, the HMAC algorithms and a missing or unknown key by itself, and Northstar further limits the algorithms to asymmetric ones that the provider lists. The cost is two new runtime dependencies, which `pyproject.toml` explains.

The HTTP is `urllib` with a handler that follows no redirects and an empty proxy list, a 10 second timeout and a 1 MB cap, because the provider's address is an operator setting but a redirect or a proxy variable would send the client secret somewhere else. Discovery must name the configured issuer, and any address in it must be HTTPS, so a compromised discovery document cannot move the token request.

A login is a row of hashes (state and browser binding) and the values only the server needs (nonce, PKCE verifier, return path, settings fingerprint), consumed by the first return that finds it, even a failing one, so a captured address can be used once at most. The browser binding is a second secret in a cookie limited to `/api/auth/oidc`, so a state copied into another browser fails. Every failure redirects to `/login?oidc_error=CODE` with a code from a fixed list. Provider text, token contents and claims are never put in the address, because proxies log it and whoever stands behind the person reads it, and what failed is in the server log in words that hold none of them.

Throttling counts only what looks like abuse: a bad state, a wrong binding or an invalid token. A provider outage, or a person who is not allowed in, does not use up the household's allowance. The counts are kept under their own kind, so no email a visitor types can be the same key as an OIDC count. A change of issuer or client ID ends OIDC sessions without a revocation hook: the session records the settings fingerprint it was made under, and the check on each request compares it.

Local sign-in being off is enforced at the password endpoint (403 before the throttle or the password check), not only hidden on the page, because a hidden button does not stop a request. That belongs to step 4's page work only in part: the enforcement is here because the flow is not safe to switch on without it.


### The sign-in page asks which ways are on, shows nothing to sign in with until it knows, and starts OIDC by navigating (#169)

The page cannot know whether password sign-in is off, so it asks a small public endpoint, `/api/auth/methods`, whose answer holds only three facts and nothing a stranger could use (not the issuer, client ID or secret). Until it answers, the page shows its heading and no form: with password sign-in off, a form that flashed up and went away would invite typing a password into a page that will refuse it. If the question cannot be answered the page shows the password form, not the provider button, because the server is the one that refuses what is not allowed and a failure to ask must not lock out the one way that works everywhere.

The provider button navigates to Northstar's own `/api/auth/oidc/login`, with the address asked for, and the server redirects on to the provider. It is not a form post: the content security policy allows `form-action 'self'`, and a form whose redirect leaves the site would be refused in browsers that check redirects.

A failure comes back as a code and the page chooses the words, so nothing the provider sent, or anyone put in an address, is ever shown. The three agreed sentences are used as they are. The wording of the other codes was written with the screens and is for review.

A user's Sign-in is derived, not stored: a usable password means local, a binding to any issuer means OIDC. The list asks for the stored hash only to test it with the same function sign-in uses and never sends it. A person with no password does not get the change-password form, because it asks for a current password that does not exist, and the server refuses that request in any case.


### An account's class is its type's class, not a second column (#181)

`accounts.class_id` was a copy of `account_types.class_id`: the account determines its type and the type determines the class, so the class is a transitive dependency, and a composite foreign key from `accounts (type_id, class_id)` to `account_types (id, class_id)` existed only to keep the copy in step. Migration 0019 removes the column, the composite key and the `UNIQUE (id, class_id)` on `account_types`, and every read now gets the class through the type. Behaviour does not change: editing an account's class still picks a type in the new class and still says how many balances it affects (see "Editing an account's class is allowed and rewrites history"), and only the type is stored. Rejected: keeping the column, which leaves two places that must agree and a key that is there to enforce it.

The composite key also did one more thing, refusing a change of a type's class while an account used it, which would reclassify every one of its accounts and rewrite net worth for every past date they cover. A trigger on `account_types` keeps that in the database. It reads `accounts` itself, not `live_accounts`, because a deleted account keeps its type so that it can be restored. Because the trigger reads `accounts`, a later rebuild of that table must drop it first and create it again afterwards, as it must the views, and the migration runner's test of a rebuild does.

A rebuilt table forgets how far its `AUTOINCREMENT` counter had got, so the id of a deleted row could be given to a new one. A type can be deleted, so the migration copies the counters of both tables and puts them back, and a test deletes the newest type before the upgrade and checks the next one gets a higher id. The earlier rebuilds of these two tables (0004 and 0010) did not keep them, and a released migration is not edited. ### The list engine reads any schema through a registry, and a key is a path of relations (#184, step 1a)

The engine in `northstar/lists/` knows nothing about Northstar's tables: it is given a connection and a registry, and it was built and checked against a second, unrelated schema (a generated one in the tests, and a larger synthetic dataset kept outside the repository) so that no list could depend on the household's shape. A table's entry says what the schema cannot (the display column, the columns that may be offered with their kinds, which are searchable, whether people may walk into it, what is denied, its record page), and relations are read from the database's foreign keys, so none is written twice. Only a foreign key to the target's primary key is a relation, because only that is certain to give one row for each row; a composite key is not one. Rejected: a registry of relations written by hand (it drifts from the schema), and definitions in the database (see the lists design: capability and wiring stay in code).

A column is named by a key, a path of relation names ending in a column or a relation, such as `site.area.lead.name`. A relation's name is its foreign key column without `_id`, so a table reached in several roles has a separate name, label and join for each, and a relation as the last part of a key means the display value of what it points at. No table may appear twice in a path, which cannot loop, so a relation back to a table already in the path (a table that points at itself, such as who created a user) is refused, and a path may follow at most six relations, a safety limit set by the deepest path in the development dataset. A table marked not walkable can be reached as a display value but not entered. A column that is not offered, or is denied, is not a column at all: asking for it is the same refusal as asking for one that does not exist.

Every name in the SQL comes from the registry or the schema and is checked as a plain identifier, every value is a parameter, and every join is on a primary key, so the rows are the table's rows exactly once whatever is shown. Sorting puts empty values last in both directions, compares text without regard to ASCII case, and ends with the record's id. Text "is empty" matches no value and an empty one, because a person cannot tell them apart. A timestamp is shown and compared as its UTC date. A scaled integer (hundredths of a degree) is typed as a decimal and refused, never rounded, when it has more places than its scale. A group's size is a window count over all matching rows, so it is the same on every page.

What is not decided here: the money kinds (a filter's decimal is read in which currency's digits) are step 1b, and the saved preferences and filters arrive with the steps that use them.


### Amounts are compared by the number shown, and a worked-out value is a column of a view (#184, step 1b)

A column of amounts mixes scales: dollars have two places, yen none. The list engine has one generic kind for it, `ScaledBy`, an integer whose scale is a column (of a record it points at, or of the same row), and it compares and sorts by the number a person sees, normalised exactly to thousandths (an integer times 1, 10, 100 or 1,000, never a float). So 10 yen and $10.00 are equal, a filter "at least 1,000" means 1,000 in each row's own unit, a typed amount may have up to three decimal places, and no row can equal a value with more places than its own scale. Rejected: comparing raw minor units, which puts $10.00 level with 1,000 yen, something no screen shows. Whether a column mixes currencies is Northstar's knowledge, not the engine's: it sees a value, a scale and a unit, and a row shows `{value, scale, unit}` for the page to write.

A value that has to be worked out (Reporting value, a balance in the system currency) is a column of a view, so the database sorts, groups and filters by it like any other. The view is `live_balance_values` (migration 0020). Its arithmetic needs exact decimals, which SQLite does not have and whose integers overflow into floats, so it calls `northstar_convert`, which is `northstar/conversion.py` registered on every connection `db.connect` opens: the same `convert` net worth uses, written once. The engine has no idea what it is. A first version gave the engine a "computed column" kind that called a function for each row and passed the answers back to SQL as a JSON parameter; it was about 150 lines more engine, slower, and gave the engine its own idea of conversion, so it was dropped for this. Rejected: doing the arithmetic in SQL, which overflows 64 bits for the largest amounts.

The price of a function in a view is that the view can only be read through a connection that registered it. Creating the view, a table rename under it, the integrity check and the online backup all work without one (tested), and every view in the database must be readable through `db.connect` (tested), so a missing registration fails a test, not a request. Opening the file in the `sqlite3` shell fails on `live_balance_values` only. A later rebuild of `accounts` or `balances` drops and recreates this view with the others, and the runner's rebuild tests do.

The view finds the rate with the same subquery as `account_days` (the latest rate of the currency on or before the balance's own date, never a later one), so that rule is written twice in SQL until net worth moves onto the same view, and a test compares the two for every balance. A balance with no rate yet, or no system currency yet, has an empty value, never zero: it sorts last and an empty filter finds it. The message "No CHF rate" is the page's, written from the empty value and the Value column's unit.

A registry entry can be a view that is based on a table (`based_on`): a view has no foreign keys, so it takes its key and its relations from that table, keeping those whose column the view has. A test fails if an engine module imports anything outside the standard library, `northstar.errors` and itself, or names a currency, a balance or an account.

A typed number too large to store is refused. The first version of the engine passed one to SQLite, which would have failed as a server error instead of a message.

A table is a list's table when it has an entry in `northstar/listdefs/tables.py` (or a view based on it does), or it is named in `NOT_LISTABLE` with the reason, and a test fails for a table that is neither, so a new table forces the decision. A foreign key to a table that is deliberately not offered (the loaded catalogs, the application's own tables) is not a relation a person can follow, while a foreign key to a table that was merely forgotten is a mistake found when the registry is read. The derived columns of an account (its latest balance, how old it is, whether it is stale, how many balances it has) move to the step that makes Accounts a list, which is the first to need them, as views in the same way.


### Every list is read through one POST endpoint, and a column opens a record page as data (#185, step 2a)

`POST /api/lists/{key}` takes the request document the engine already validates and answers the page of rows, the count of every matching row, the page shown, and a description of each column (its label, its full path of labels, a short code for its kind, and whether it opens a page for this person). A read is a POST because the request is nested (filters, columns, sort) and a filter's values are household data: a query string goes into the access log of the application and of any proxy in front of it, a body does not. Rejected: a GET with the filters packed into one parameter. The same reason does not cover the page itself, whose address carries the view's state so that a refresh and Back restore it and so is logged when the page is loaded; whether to remove query strings from the access log is its own, smaller decision. The app's rule that a change from another site is refused applies to a POST and so to this read, which is harmless.

An unknown list is a 404, a list defined as `admin_only` is a 403 for anyone else (the flag is data on the definition, so the endpoint adds no rule of its own), and a request that breaks a rule is a 422 with the engine's message.

A table's entry names the route of its own page as a pattern (`/accounts/{id}`, `/currencies/{value}`, where the value is the display value, quoted) and, if it is for a role, which. A relation column opens the page of the record it points at and the display column of a list's own table opens that table's page, only for a person who has the role. The rows carry the routes (`_links`), so the engine still returns plain values and the page draws a link. A relation with nothing in it has no link. The engine knows roles only as names the caller hands it: it does not know what an admin is.

A person's page size is the table `user_list_prefs` (migration 0021): one row for each person and list, saved by `PUT /api/lists/{key}/page-size`, and a list that has none uses its own default. A request that names a page size uses it for that request only. It is an audited household table like the other per-person settings, and the page size is not a logged field (as the theme is not), so changing it leaves no operation in the change log and only the row's creation does. The columns a person chooses will be added to this table by the step that offers them. A list that does not exist has no page size to save, and the size must be exactly a whole number of 10, 25, 50 or 100.


### The list view is one component on TanStack Table 9, and the address is its state (#185, step 2b)

`ListView` draws any list from `POST /api/lists/{key}`: a search box, a table with sortable headers, a footer with the range, the page and the page size, and loading, failure, empty and no-match states. It is built on `@tanstack/react-table` 9.3.1, pinned exactly (MIT; with `@tanstack/table-core` 9.3.1, `@tanstack/react-store` 0.11.2 and `@tanstack/store` 0.11.2; `npm audit` finds nothing). The reason: the library holds the model of sort and page state and the header and pagination helpers, and leaves markup, styling and accessibility to the app, and its server mode (`manualSorting`, `manualPagination`, `rowCount`, confirmed in the 9.3.1 type definitions) leaves the sorting and paging to the server, which is where the design does them. The later steps (filters, grouping, column order and visibility) have features of the same library to build on. Rejected: hand-written sort and page state, which is code to keep for each of those later steps, and version 8, an old major. Measured on 9 November 2026: with the component included the JavaScript goes from 346.46 kB to 390.47 kB (101.63 to 115.61 kB gzipped), and the CSS from 26.81 to 28.57 kB (5.63 to 5.92 kB gzipped).

The view's state is the page address, `?sort=-date&page=2&q=savings` (a minus sorts descending), so a refresh, a copied link, Back and returning from a record restore it. A default is not written, so a plain list has a plain address, and anything missing or malformed is the default, never an error, because an address is typed and pasted. A sort and a page are history entries and so Back steps through them; the search replaces the address as it is typed (`replaceAddress` in the router, after a short pause), so Back does not step through every letter. The page size is not in the address: it is the person's saved choice (`PUT /api/lists/{key}/page-size`), used from their next visit, and changing it returns to the first page. Filters and grouping will join the address in their steps.

A click on a header sorts ascending and a second click reverses (it never removes the sort), and the column menu offers both directions; Group by, Filter and Hide join that menu later. The list's own sort is shown before anyone chooses one, because the server says which sort it applied. Numbers are lined up on the right and written in the person's formats by the kind of column: an amount carries its own currency, a decimal stored as a whole number its scale, and a timestamp is shown as its UTC date. An overtaken response is ignored (the existing `useLatest` rule), and the rows stay on screen, marked busy, while the next page loads, so a sort does not blank the table. A failed request offers to try again and keeps the last good view.

What only a list's own page can know is a small `ListConfig` beside the list's key: a column drawn another way (the message "No CHF rate" for an empty converted value is the page's, written from the value and the Value column's unit), a row's menu with its dialogs and which items are disabled and why, and what an empty list says. The component has no list in it, and the Balances page of a later step supplies only that.

Not decided here, and still open: whether to strip query strings from the access log, since the address now carries the view and a page load is logged with it.


### A list offers a tree of columns made by the rules that check a request, and a filter's choices are what the list has (#186, step 3a)

`GET /api/lists/{key}/fields` answers the tree of everything a person can show, sort or filter by: the list's own columns, and under each relation the columns of the record it points at. A relation is a column in its own right (it shows the display value of what it points at, and is filtered by a choice of those records) and a branch where its table has more to offer. The tree is made through the same `resolve` that checks a request, so it offers a key exactly when a request would accept it: nothing denied, nothing past the depth limit, no table twice in a path, no walking into a table that only shows its name, and the display column of a related record not repeated under the relation. Relations are sorted by label, because the database lists foreign keys in its own order, which a person should not be shown. Each node says its key, its label and the whole path of labels, its kind, its scale if it is a decimal held as a whole number, its operators with their labels (a Yes or No column offers "is empty" only when it can be), and whether it has choices to pick from. The columns drawer of a later step reads the same tree.

`GET /api/lists/{key}/choices/{field}` answers what a filter on one column can pick from: the declared values of a choice, or, for a relation, the records that the list's own rows point at, each with its id, its display value and the table's tell-apart detail where it declares one. They are the list's records, not every record of the target table, so a filter never offers a deleted account (the list leaves its balances out) or an account that has no balance, and the list's own scope applies. They are in order without regard to case and then by id, at most 500, with `more` when there were others. Rejected: every row of the target table, which would offer deleted records and ones the list never shows. A list whose choices run past 500 would need a search as you type; no list does yet. A column that has nothing to pick from is a 422.

Both are for any signed-in person, with the same 404 and 403 as the list itself.


### Saved filters are one table, private or shared, with the defaults enforced by the database (#186, step 3b)

`list_filters` (migration 0022) holds a name and the conditions of a filter for one list, as JSON that the list engine checks when it is saved and again when it is used. A person's own are private to them (`owner_id` set). A filter with no owner is shared: everyone who can see the list sees it, and only an admin makes, changes or removes it. Another person's private filter is not found, never forbidden, even to an admin, so its existence is not told; a shared one is forbidden (403, a new `NotAllowedError`) to anyone else.

A person has at most one default filter for a list and a list at most one shared default. One partial unique index says both, because a shared filter's owner counts as 0, and so the database refuses a second even if the application is bypassed. Making a filter the default takes the mark from the one that had it in the same transaction, so a person never meets the refusal. A list opens with the person's own default, else the shared default, else no filter. A name is unique for one owner and list ignoring ASCII case, and among the shared ones; a private filter may have a shared filter's name. A person can keep at most 100 for one list. The conditions are never SQL, are at most 20,000 characters, and are stored compactly in the same form however they were sent.

The default is applied by the list's own endpoint, and only when the request names no filters. A request that names filters, even an empty list, gets exactly those, so a person who cleared a filter stays cleared after a refresh and the default does not come back. The answer says which conditions were applied, which saved filter the list opened with, and which of its conditions were skipped. A condition that names a column the list no longer offers is skipped with its reason, never an error, so a list change cannot make a saved filter unusable; the saved filters themselves report these as `problems`, so a page can mark them.

Every change is logged, the default mark included, because a shared filter is configuration that admins change; a private filter is the same table and so logged too. Rejected: a separate table for shared filters (the same columns, and the one-default rule is one index), and ids of saved filters in the page address (a copied link must mean only its conditions; see the list view's decision).


### The filter drawer edits a draft, and a saved filter only fills it (#186, step 3c)

A list's filters are made in one drawer opened from a Filters button. What is typed there is a draft: nothing reaches the list until Apply changes, and Cancel or Escape throws it away. Applying writes the conditions into the page address (`filters=<JSON>`, and `filters=[]` for a filter cleared on purpose, so the default does not return by itself), goes back to page 1 and shows each condition as a chip. Removing a chip applies at once. A saved filter's id is never in the address: a copied link means only its conditions, and what a saved filter later becomes cannot change it.

Choosing a saved filter only fills the draft, exactly as if the conditions had been typed, so it can be adjusted before it is applied. A filter that has been changed since it was loaded says so. Save replaces the loaded filter's conditions, Save as new keeps it and asks for a name, and neither applies or closes the drawer. Making a filter the default is a property of the saved filter and is saved at once. Someone who cannot change a shared filter can use it and save a private copy. A condition a saved filter has that the list no longer offers is left out of the draft with a message, and saving drops it.

Add filter offers every column the list's field tree gives, shown or not, as the same tree the column drawer will use, and one column takes one condition. The value controls follow the column's kind and operator, and a typed number is read in the person's own decimal and group marks and sent with a point. A mistake is not said on a row nobody has touched yet; it is said once something is typed, and for every row when Apply is pressed with something incomplete, which then applies nothing. The server still checks every condition.

The saved-filter picker is the drawer's own, so the page needs no list of filters to draw; a page passes only a title and whether the person is an admin, which decides whether "for everyone" is offered. Rejected: applying a saved filter by name straight from the toolbar (it would be a second way to filter that skips the draft), and an id in the address.
